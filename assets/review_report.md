# 本轮文档审阅记录

按“系统工程师能否判断职责与部署、设计工程师能否写出请求和响应”两个标准，进行作者自检和独立交叉审阅。以下是实际发现并修正的问题，不是在线系统验收。

## 特征服务修订审阅（上一轮）

| 轮次 | 发现的问题 | 修正结果 |
|---|---|---|
| 边界审阅 | 特征模块在部分文档仍位于 PaiRec 进程内，另一些图又像独立服务 | 全套统一为独立 FeatureService；PaiRec 通过客户端查询，Redis 访问在服务内部 |
| 数据审阅 | “有几类数据库”混淆物理产品与逻辑集合 | 明确两类存储、一类在线特征数据库；四类核心数据、六组业务键和发布清单 |
| 接口审阅 | 只说“取用户历史”但不清楚向量、词项、SID 在何处取得 | 三个明确方法，用户表示与历史指纹关联；正反向 SID 查询分别定义 |
| 调用审阅 | 两阶段读取被误写为固定两次 RPC | 正常示例为 PaiRec 三次、生成服务一次；Redis 拆批另计 |
| 映射审阅 | 单值 SID map 会覆盖共享编码的物品 | 反向 value 使用 item_ids 数组，同码按数值 ID 升序；保留生成次序并稳定去重 |
| 源码审阅 | 原版 OneTrans 图使用未实现的请求级 KV、ready 句柄和释放接口 | 改按当前 /ingest、/rank、TSV、参数服务和用户级 KV；/score 能力单列 |
| 时序交叉审阅 | OneTrans 参数查询被画在 KV 命中分支内 | 按源码改为参数查询、特征编码、KV 查询，然后决定是否执行候选 Transformer |
| 时序交叉审阅 | 无历史时仍画为发送 /ingest | 当前触发器增加“缺失或空历史不投递”分支；目标严格编排明确失败 |
| 协议交叉审阅 | 部分图给当前 OneTrans 加上计划中的 bRPC 桥 | 主链统一保留 HTTP，未来桥作为独立后续选择 |
| 类型交叉审阅 | 用户上下文响应未定义；逐项缺失状态不统一 | 固定四个视图状态和数据字段；批量结果按位置返回，缺字段用 null/missing_fields |
| 可读性审阅 | 15 维数组被当作通用物品事实；两套 OneTrans 字段配方混用 | 新特征保存命名业务字段；现有 TSV 配方单独列出；旧附件显式归档 |
| 可读性审阅 | 多套无关联用户例子、未解释的 sigmoid、物理视图名称不一 | 用户 1 贯穿；明确分数含义；统一五视图名称；未核实数据覆盖醒目标注 |
| 一致性审阅 | 表示查询省略版本、去重未说明是否保序 | 补 release_id/sid_version；采用 stable_unique，按输入位置和来源次序处理 |
| 最后一次接口审阅 | 历史 SID 缺失写成“可以剔除”，实现者仍需自行选择 | 首期默认任一历史 SID 缺失则生成分支失败；生成输出反查缺失记录后跳过，两个方向分别定义 |

审阅没有把所有实现细节放进系统总图：最外层只保留召回与排序阶段，服务和模块内部另画。原工程名只用于源码定位，业务角色使用编排、特征、召回、精排等名称。

旧接口附件已移至 archive_v2，新的场景和请求模板不会偷偷改回完整特征 OneTrans 方案。真实输入证据与模型运行值分开：上一轮真实证据附件没有真实向量、SID 或模型分数时保留缺失。本轮按用户要求另增教学附件，允许显式标记的示例数值，不改变真实证据内容。

机器检查结果见[静态验证](validation.json)和[渲染验证](render_validation.json)。这些检查不能替代服务部署、模型前向或数据库运行验收。

## 按 4+1 定义重新拆分与可读性审阅（前次修订）

依据 Kruchten 原文重新检查各视图承担的问题，上一版“增加服务与数据层”的调整不足以解决逻辑视图混入运行调用的问题。本轮重新拆分，而非继续向原图增加节点。

| 发现的问题 | 修正结果 |
|---|---|
| 逻辑视图把阶段流程、服务和数据库调用混在一起 | 改为同级业务职责的组成图、领域对象关系图和责任表；公共特征与版本管理单列，箭头含义明确 |
| 内部业务字段看起来像已有接口字段 | 说明 sources、fusion_order 等是概念模型字段，客户端负责与实际接口对应；补断言中变量的含义 |
| 开发、进程、物理视图的边界不鲜明 | 开发只画源码静态依赖；进程分别画执行单元通信和请求内同步；物理显式分配节点、设备与文件卷 |
| 场景不足以检验架构边界 | 保留数据库交互，并检验候选缺失、历史状态失败、同用户覆盖风险及人工发布；入口与返回均经过 Nginx |
| 详细请求代码依赖未在当地解释的概念 | 就近说明数据视图、版本、历史摘要、SID 正反查、Provider、PS、KV、展平参数、TSV 槽名和分数含义 |
| 示例数据结构与业务转换需要读者自行猜测 | 展开历史编码转换，解释 Redis 记录对应、同码多物品展开、融合顺序、资格过滤及稳定排序 |

架构定义审阅与独立读者审阅完成后，再逐项核对修正。后者从用户上下文一直追到最终响应，确认主流程无需依赖外部文档中的隐含概念；没有继续增加不影响理解的解释。OneTrans 当前数据来源和接口、目标特征服务、离线装载、人工干预、分层画图及外部压力回放等约束均保留。

## UML 语义、具体接口样例与仓库独立阅读审阅

| 问题 | 修正 |
|---|---|
| 普通结构图容易被统称 UML 图 | 逐图标明图法；新增统一图例；明确 39 张普通图、1 张概念类图、16 张时序图 |
| 实心菱形暗示尚未约定的对象生命周期 | 候选与来源记录、结果与评分条目改普通关联，补单次请求的数量语义；算法先后不放入类图 |
| 离线文件交付误画成调用返回 | 改为构建调用模型生产、接收返回、提交装载、校验返回、发布的成对交互 |
| 并行任务与同步箭头容易混淆 | 说明 PaiRec 参与者包含并行子任务，同步等待只属于发起调用的任务；OneTrans 场景限定命中成功路径 |
| 辅助函数不知来自何处 | 明确本文自定义 call_meta/feature_meta、字典展开、预算计算和配置来源，非 SDK/RPC |
| 读者要自己把伪代码展开才有完整载荷 | 正文增加完整稀疏召回 JSON；附件提供同一用户请求的 10 组完整业务接口输入输出，并与主样例校验 |
| 本机绝对路径与外部源码依赖妨碍 clone 阅读 | 改相对链接，随仓库保存已引用源码与前期资料的 HTML 快照；保留行号和 hash，避免执行原文件内容 |
| 校验及渲染依赖固定机器路径 | 默认只校验仓库，源数据复核显式选择；渲染使用正常环境或明确指定的可选路径；阅读无需安装依赖 |

UML 符号核对依据、每种图的适用范围及并行含义见[图法说明](../DIAGRAM_NOTATION.md)。标准核对与逐图语义审阅和可解析性检查分开：渲染成功本身不证明 UML 语义正确。

## 逻辑架构与进程部署映射复核

重新对照 Kruchten 原文检查后，上一版的处理链与功能分解只覆盖了功能分析，未充分表达核心抽象间的协作；按 CPU/GPU 命名的节点角色也不能唯一确定部署归属。本次修订集中处理这两个问题。

| 问题 | 修正 |
|---|---|
| 逻辑图仍主要表达数据流或动作清单 | 改为六个逻辑单元及业务能力依赖；第二层表达召回策略、候选获取、历史表示、模型输入之间的结构关系，其余职责用接口与责任表展开 |
| 逻辑依赖与代码依赖容易混同 | 分别定义“需要业务能力”与“导入/编译代码”；逻辑单元不与独立服务或源码目录一一对应 |
| 物理节点没有明确指主机、容器还是服务 | 采用目标 Host→进程实例布局；两图使用同名主机，明确同机、跨机、CPU/GPU及文件归属，容器/Pod作为映射选项说明 |
| DataSystem被简化为一个共享远端节点 | 模型主机各配置本机worker，共用集群etcd；各主机内存独立，worker通过网络传输，不能误读成共享同一块内存或容灾副本 |
| 部署草图可能把库或执行器画成独立进程 | 核对生成服务的进程内TensorRT-LLM执行器；OneTrans两端选C++CPU基线，各自装载文件；参数服务启动后装载内存表 |

新增两份已有部署配置的只读证据快照，便于克隆后核对DataSystem worker集群参数及Milvus内嵌etcd、本地存储。已有局部Kubernetes脚本不作为整套目标系统已经部署的证据。独立架构审阅与源码审阅分别核对视图用途和部署事实，随后检查渲染布局及离线阅读。

## L1 合并与 Pod、容器部署边界复核（最新修订）

本次修订取代上一节记录中的七台 Host 布局、历史与候选强制跨机、每个模型主机配置 worker 以及固定 CPU 基线。这些安排没有足够部署依据，不能作为当前系统约束。

| 审阅问题 | 修正结果 |
|---|---|
| 两张逻辑图拆得过细，却没有增加足够信息 | 合成一张 L1，直接展开三路召回及历史计算、候选打分；保留编排、召回合并、重排、特征服务与能力依赖。业务契约和数据责任只保留一份表 |
| 主机归属缺乏实际依据 | 两张物理图改为 Pod 包含容器、容器列出进程；不指定主机、实例数、worker 数量或调度位置 |
| 目标容器边界容易被当作已有部署 | 增加简明依据表：生成、Milvus、DataSystem 有局部部署配置；OneTrans 只有多进程启动示例，两个角色的容器化仍待补 |
| 服务名掩盖实际进程关系 | 生成入口与 TensorRT-LLM 保持同一进程；两个 OneTrans 角色运行同一程序；worker 与 etcd 独立部署，共享数据域不等于连接同一 worker |
| 关联文档仍暗含主机分配 | 同步阅读入口、图例及 OneTrans、RPC 引用；召回模块的 HTTP 桥明确为可选适配方案，撤掉未经确定的同机要求 |

独立逻辑审阅确认 L1 保持业务能力依赖，没有改成执行流程；部署源码审阅确认当前事实与目标安排分开。新增生成容器部署配置的只读快照，保留提交、行号与哈希。实际查看 L1 及两张部署图，检查分组、文字和连线；全套现为 55 张图（16 张 UML 时序图、39 张普通示意图）。用户 1 的请求样例与接口载荷不变，继续执行渲染、链接、源码快照和样例一致性检查。
