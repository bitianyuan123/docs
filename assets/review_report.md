机器检查结果见[静态验证](validation.json)和[渲染验证](render_validation.json)。这些检查不能替代服务部署、模型前向或数据库运行验收。

| 问题 | 修正 |

## 逻辑架构与进程部署映射复核

重新对照 Kruchten 原文检查后，上一版的处理链与功能分解只覆盖了功能分析，未充分表达核心抽象间的协作；按 CPU/GPU 命名的节点角色也不能唯一确定部署归属。本次修订集中处理这两个问题。

| 问题 | 修正 |
|---|---|
| 逻辑图仍主要表达数据流或动作清单 | 改为六个逻辑单元及业务能力依赖；第二层表达召回策略、候选获取、历史表示、模型输入之间的结构关系，其余职责用接口与责任表展开 |
| 逻辑依赖与代码依赖容易混同 | 分别定义“需要业务能力”与“导入/编译代码”；逻辑单元不与独立服务或源码目录一一对应 |
| 物理节点没有明确指主机、容器还是服务 | 采用目标 Host→进程实例布局；两图使用同名主机，明确同机、跨机、CPU/GPU及文件归属，容器/Pod作为映射选项说明 |
| DataSystem被简化为一个共享远端节点 | 模型主机各配置本机worker，共用集群etcd；各主机内存独立，worker通过网络传输，不能误读成共享同一块内存或容灾副本 |
| 部署草图可能把库或执行器画成独立进程 | 核对生成服务的进程内TensorRT-LLM执行器；OneTrans两端选C++CPU基线，各自装载文件；参数服务启动后装载内存表 |

新增两份已有部署配置的只读证据快照，便于克隆后核对DataSystem worker集群参数及Milvus内嵌etcd、本地存储。已有局部Kubernetes脚本不作为整套目标系统已经部署的证据。独立架构审阅与源码审阅分别核对视图用途和部署事实，随后检查渲染布局及离线阅读。

## 模块规范与执行负载复审（最新修订）

本轮按最新系统视图规范复审 02—10，并新增 Redis 专题。此前部分模块的逻辑图仍是处理流水线、开发图含网络调用、物理图只列服务关系；这些不符合各视图用途，已分别重绘。08 的接口推演保持原样例，09 补充负载验收边界，10 明确 Cluster 跨槽批读要求。

| 重点问题 | 复核与修正 |
|---|---|
| 前期 PaiRec 分析可能把框架默认行为算到目标场景 | 单独取得官方 v2.6.2 模块，与当前扩展、目标 RecommendEngine 区分；框架额外完整路径和默认 Rank 扇出不自动计入本场景 |
| 协程等待被等同于阻塞一个 OS 线程或一次 futex | 按 Go 官方机制解释网络等待、channel、WaitGroup、可运行队列和同步 CGO；GOMAXPROCS 不代表整个进程的线程或 CPU 上限 |
| 当前历史闸门被误当成成功凭据 | 说明队满丢弃和失败也会放行、ingest 调用方只验 HTTP 状态、rank 等待超时后仍重查；与目标 accepted 汇合分开 |
| OneTrans 看起来只有历史、候选两个抽象进程 | 展开 HTTP 接入、阶段池、攒批线程和 Python 桥；明确异步投递后复用接入线程，响应仍由完成线程直接发送 |
| 线程池被默认为硬容量和统一过载处理 | 源码确认 pending 软检查、连接/攒批队列无显式硬上限、计算池提交异常缺少捕获边界；这些是静态发现，未做故障注入 |
| 计算与内存开销只按模型大小估计 | 按形状计算历史张量、候选输入和参数响应；区分进程常驻权重、Go/原生缓冲、C++复制、Python字节边界及设备传输 |
| Redis 被简单写成单线程、每次请求固定四条命令 | 以参考版本解释命令线程、网络IO线程、后台任务及持久化子进程；单实例四批与Cluster拆分、pipeline、连接等待分别说明 |
