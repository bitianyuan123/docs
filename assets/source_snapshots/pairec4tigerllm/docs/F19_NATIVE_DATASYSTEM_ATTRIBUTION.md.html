1# F19 Native DataSystem Request Attribution
2
3## Contract
4
5PaiRec keeps its current response path. It does not wait for DataSystem Set completion.
6The native TensorRT-LLM process emits one later completion event for each PaiRec UUID:
7
8```json
9{"event":"datasystem_request_complete","request_id":"<uuid>","get_count":2,"get_us":12000,"set_count":3,"set_us":19000,"get_failed_count":0,"set_failed_count":0,"pending_count":0,"unknown_count":0,"attribution_complete":true}
10```
11
12The same event now carries the V3 native Executor phase breakdown:
13
14```text
15executor_queue_us
16add_sequence_us
17prefill_gap_us
18add_token_us
19decode_gap_us
20finalization_gap_us
21remove_sequence_us
22native_lifecycle_us
23native_accounted_us
24native_closure_error_us
25```
26
27`prefill_gap_us` is the interval from KV sequence allocation to the first generation
28`addToken`; `decode_gap_us` is the sum of intervals between later `addToken` calls;
29`finalization_gap_us` is the interval from the final KV update to sequence removal.
30These gaps include scheduler and GPU execution between KV-manager calls. The detailed
31`attribution_lookup_us`, `sequence_lookup_us`, and `kv_update_us` fields are subsets of
32`add_token_us` and must not be added to the lifecycle total. `phase_record_us` reports
33the tracker bookkeeping cost; it is already present in a following gap and is also not
34an additive phase.
35
36The gateway emits one `trt_executor_request_complete` event per Executor sample after
37the measured runner interval has ended. It breaks runner time into request construction,
38the enqueue call, waiting for the final response, and response extraction. Logging is
39therefore outside the measured interval. Gateway phase clocks and this event are enabled
40only with `TRTLLM_DATASYSTEM_REQUEST_ATTRIBUTION=1`; the disabled path does not collect
41these timings.
42
43The correlation path is exact:
44
45```text
46PaiRec UUID
47  -> brpc RecommendRequest.request_id
48  -> gateway monotonic uint64 correlation ID
49  -> Executor Request.clientId
50  -> LlmRequest.mClientId
51  -> KVCacheManager sequence
52  -> DataSystem Get/Set scope
53  -> native completion event joined back by PaiRec UUID
54```
55
56Set belongs to the request whose allocation evicts and offloads a block. Get belongs
57to the request whose cache reuse onboards the block. Operations without a request
58context are reported as unattributed and are never assigned by timestamp proximity.
59
60The tracker closes only after every native Executor sequence for the Recommend has
61been removed and every tracked operation has returned. The default TTL is 30 seconds;
62expiry emits `attribution_complete=false` instead of silently dropping the sample.

64## Build
65
66Run on the machine that owns the patched TensorRT-LLM source and ARM64/GPU runtime:
67
68```bash

76
77The source tree must already contain the project DataSystem KVC modifications. The
78F19 patch is idempotent, but it is not a replacement for those earlier modifications.
79
80The build script idempotently reapplies the current repository patch by default, so
81an already-patched V1/V2 tree also receives managed-source updates such as the V3
82phase timing marker. Set `APPLY_PATCH=0` only for a deliberate compile-only rerun.
83
84The recovered worker1 history contains both `zcx-pairec-image:v1.1` exploration and
85the successful `zcx-pairec-trtllm-brpc-sdk:parallel-get-ctx224-v1` build container.
86Only the latter was followed by successful checks for `libcudadevrt.a` and
87`libcudart_static.a`; it is therefore the first candidate for the native build.
88
89The script consequently uses two isolated build stages:
90
911. `TRT_BUILD_IMAGE` is selected only after an executable preflight confirms the
92   ARM64 compiler and both CUDA static runtime libraries. The historical
93   `zcx-pairec-trtllm-brpc-sdk:parallel-get-ctx224-v1` image is tried first. The
94   selected image builds only `libtensorrt_llm.so`.
952. `GATEWAY_BUILD_IMAGE` first tries the recovered historical SDK image
96   `zcx-pairec-trtllm-brpc-sdk:parallel-get-ctx224-v1`, then local BRPC inference
97   images. Every candidate must pass an executable preflight for protobuf headers
98   and the brpc C++ SDK. The selected image builds only `brpc_inference_server`
99   against the stage-one native library. It does not need `protoc`: the F19 build
100   enables checked-in C++ sources generated by protoc 25.1 for the image's
101   Protobuf C++ 4.25.1 headers and runtime.
102
103Both containers mount the host TensorRT-LLM tree at `/TensorRT-LLM`; the gateway
104container mounts this repository at `/mnt/pairec-src`. The default build parallelism
105is capped at 32 even when worker1 reports hundreds of CPUs. Set `JOBS` explicitly
106only when a different memory/CPU tradeoff has been validated.
107
108The build script writes both artifacts to a staging directory. It publishes them to
109`/home/zcx/pairec-f19-runtime/{bin,lib}` only after both stages, marker checks and
110gateway `ldd` validation pass. Override either stage only with a locally verified
111ARM64 image:
112
113```bash
114TRT_BUILD_IMAGE=zcx-pairec-trtllm-brpc-sdk:parallel-get-ctx224-v1 \
115GATEWAY_BUILD_IMAGE=pairec-brpc-inference:<local-brpc-sdk-tag> \
116TRTLLM_DIR=/home/zcx/TensorRT-LLM \
117  bash scripts/build_f19_attribution_runtime_worker1.sh
118```
119
120The script reproduces the two requirements discovered during the manual native
121build: it mounts only worker1's `libcuda.so.1` at
122`/host-driver/libcuda.so.1`, and adds the CUDA directory containing
123`libcudadevrt.a` and `libcudart_static.a` to `LIBRARY_PATH`. It deliberately does
124not add `/host-driver` to `LD_LIBRARY_PATH`; mounting the whole host `/lib64`
125overrode the build image's `libstdc++` and made PyTorch fail its GLIBCXX check.
126Before compiling, it reconfigures the existing TensorRT-LLM build tree with
127`CMAKE_BUILD_TYPE=Release` and rejects a cache without the Release `-O3 -DNDEBUG`
128flags. This is mandatory: the recovered worker1 cache had an empty build type and
129produced a library whose warm decode cost was about twice the historical runtime.
130It rejects unresolved gateway libraries, missing V2 attribution/V3 timing markers and
131missing output-token or Executor-phase trace fields before replacing the overlay. Success ends with
132`F19_ATTRIBUTION_RUNTIME_BUILD_OK`.
133
134The full image rebuild remains available as a slower fallback when a hostPath overlay
135is not acceptable:
136
137```bash
138BASE_IMAGE=zcx-pairec-trtllm-brpc-sdk:v1 \
139  bash scripts/build_brpc_trtllm_inference_image.sh \
140    docker.io/library/pairec-brpc-inference:k8s-arm64-v1 \
141    /home/zcx/pairec-brpc-inference-k8s-arm64-v1.tar
142```
143
144Import the rebuilt image into the Kubernetes node's `k8s.io` containerd namespace
145using the existing local image flow. Do not transfer the historical 122 GiB tar when
146the node can rebuild or receive the changed binary and native libraries directly.

148When worker1 already contains the rebuilt gateway and native library under
149`/home/zcx/pairec-f19-runtime`, deploy and validate both hostPath overlays from the
150master with one command:
151
152```bash
153bash scripts/deploy_f19_datasystem_attribution_overlay.sh apply

155
156The script backs up the current Deployment, first rolls out with attribution
157disabled to verify the executable, hashes, dynamic libraries and Health endpoint,

171REQUIRE_DATASYSTEM_ATTRIBUTION=1 \

200`attribution_complete=true`, and zero failed, pending, unknown, duplicate, missing, or

202the summary joins the later native event from `inference.log` by exact `request_id`.

205
206```bash
207NAMESPACE=pairec \
208PAIREC_TARGET=deploy/pairec-brpc-observed \

214The output prints both closure layers. Diagnose the regression from this request before
215running another enabled/disabled benchmark:
216
2171. A large `request_setup_us` or `enqueue_call_us` points to the gateway/Executor API.
2182. A large `executor_queue_us` points to scheduler admission or existing work.
2193. A large `prefill_gap_us` points to context execution after KV allocation.
2204. A large `decode_gap_us` points to token generation/model iterations.
2215. A large `add_token_us`, `finalization_gap_us`, or `remove_sequence_us` points to KV
222   management, DataSystem copy/offload, or request teardown.
2236. `runner_minus_native_us` in the single-request output isolates gateway work before
224   native admission and after native sequence removal. The aggregate summary reports
225   the same value as `runner_minus_native_ms` after converting microseconds to milliseconds.
226
227The strict 1000-request summary emits p50/p95/p99 for all of these fields and fails if
228the native phase event is absent, incomplete, duplicated, or cannot close within 100us.

268## Performance Check
269
270Measure disabled and enabled modes with alternating 1000-request runs after warmup.
271Use at least three pairs and compare pair medians. The accepted overhead budget is:
272
273- client E2E average increase: at most 0.1 ms
274- client E2E p99 increase: at most 0.5 ms
275- throughput loss: at most 1 percent
276- every disabled and enabled run runner average: at most 110 ms
277- paired output-token average difference: exactly zero
278
279Both modes must use the same image, workload, CPU limits, DataSystem endpoint, and
280cache preparation. Changing only `TRTLLM_DATASYSTEM_REQUEST_ATTRIBUTION` requires an
281inference rollout because the native process reads the flag once at startup.
282
283Run the formal paired benchmark from the master repository that controls the K8s
284Deployment:
285
286```bash
287PAIRS=3 \
288REQUESTS=1000 \
289WARMUP_REQUESTS=1 \
290  bash scripts/benchmark_f19_attribution_ab.sh \
291  | tee /tmp/f19-attribution-ab.log
292```
293
294Each pair runs `disabled` followed by `enabled`. Every round forces an inference
295rollout after setting the mode, which resets the native cache before the identical
296warmup. Images are neither rebuilt nor imported. The inner validator still checks
297business responses, trace closure, BRPC-only protocols, rerank, resource limits and
298Pod health; enabled rounds additionally require one exact native completion per
299request. Workload throughput is measured from immediately before the first request
300until the last response, excluding rollout and completion-wait time.
301
302The final result is written to the printed `summary_json` path. A passing run ends
303with both markers:
304
305```text
306classification=F19_ATTRIBUTION_AB_PASS
307F19_ATTRIBUTION_AB_BENCHMARK_COMPLETE
308```
309
310The final enabled round intentionally leaves strict attribution enabled.
311Disabled rows report zero DataSystem counts because request attribution is disabled;
312the underlying DataSystem KVC path remains configured and is not disabled by this
313benchmark.

315## Formal Result
316
317The 2026-08-11 ARM64/Kubernetes run completed three 1000-request pairs. Every round
318passed the business, trace, BRPC-only, rerank, resource and Pod-health gates. All
319enabled rounds joined 1000/1000 exact native completion events and each observed 54
320Gets plus 1995 Sets. Pair-median attribution overhead was:
321
322- client E2E average: -0.672 ms
323- client E2E p99: -1.947 ms
324- closed-loop throughput loss: 0.076 percent
325- runner average: -0.188 ms
326- runner p99: -1.000 ms
327
328That result is retained as evidence for the tracker statistics and logging path, but
329it is no longer accepted as proof for the complete attribution patch. The disabled
330mode still set Executor `clientId` and performed the request-map lookup under
331`mSequencesMtx` for every generated token. Both modes therefore shared the most
332intrusive code path.
333
334The V2 patch makes disabled mode a real no-identity baseline: it does not allocate a
335correlation ID, set Executor `clientId`, or access the native request map. Enabled
336mode keeps exact attribution but moves the request map to a dedicated mutex so token
337accounting cannot contend with the scheduler's sequence critical section. Trace
338fields 40 and 41 report output-token count and runner milliseconds per output token.
339The benchmark fails if token counts differ or if either mode remains above 110 ms
340average runner latency. The final Release validation passed this gate remotely.

342## Bounded Business Failure Handling
343
344The strict workload validates successful end-to-end recommendation requests. A
345generation can occasionally finish normally but map to no catalog item; the gateway
346then returns `code=299` (`items size not enough`) and the F20 source-quota reranker
347correctly fails closed with payload `code=500,msg=rerank failed`.
348
349Do not disable that production behavior for F19. Instead, the workload driver can
350explicitly skip a bounded number of exactly those responses and continue until it
351has collected the requested number of successful samples:
352
353```bash
354MAX_EXPECTED_RERANK_FAILURES=20 \
355REQUESTS=1000 \
356WARMUP_REQUESTS=1 \
357REQUIRE_DATASYSTEM_ATTRIBUTION=1 \
358BUILD_IMAGES=0 \
359IMPORT_IMAGES=0 \
360FORCE_INFERENCE_RESTART=0 \
361FORCE_PAIREC_RESTART=0 \
362  bash scripts/deploy_and_validate_pairec_brpc_observed.sh \
363  | tee /tmp/f19-release-1000-validation.log
364```
365
366The default limit is zero. The exception applies only when source rerank validation
367is enabled and only to the exact `500/rerank failed` contract. Transport failures,
368other application errors, malformed responses and an exceeded limit still stop the
369run immediately. Skipped attempts are written to
370`expected-rerank-failures.tsv`; `request-attempts.json` records accepted, attempted
371and skipped counts. They are excluded from the 1000 successful request IDs used for
372latency and exact DataSystem joins, while their request time remains part of the
373closed-loop workload wall clock.
374
375Health events are evaluated as a workload interval, not as Pod-lifetime history.
376The validator snapshots each Ready Pod name and cumulative `OOMKilled`, `BackOff`
377and `Unhealthy` Event count before warmup, then requires the same Pod, zero restarts
378and no count increase after the workload. Historical startup events therefore do not
379invalidate a healthy run, while any new event during validation remains fail-closed.
