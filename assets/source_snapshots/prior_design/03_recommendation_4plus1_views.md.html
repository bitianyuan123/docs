5## 0. 目标、基线与事实边界
6
7### 0.1 本轮主线
8
9建立一个依赖**未修改的官方 PaiRec**的新最小应用，自有 controller 和 `RecommendEngine` 负责推荐业务；进程内 C++ client adapter 负责原生 bRPC 通信。应用不以 8506 为最终维护分支，不复制它的 vendor、Go wire、DeepFM、压力模块或旧编排插件。
10
11默认路径如下：
12
13```text
14客户端 → 官方 PaiRec HTTP 入口 → 自有 controller → RecommendEngine
15                                                    │
16                        Go 业务接口 → CGO / 稳定 C ABI（进程内）
17                                                    │
18                                     C++ native client adapter
19                                  ┌─────────────────┼─────────────────────┐
20                        Redis RESP/TCP       bRPC baidu_std/TCP    bRPC baidu_std/TCP
21                                  │                 │                     │
22                               Redis        C++ server adapter     Gen 原生服务
23                                             │ 本机 HTTP             │
24                                      Dense / Sparse / S / NS      TRT + DataSystem
25```
26
27CGO/C ABI 是语言和依赖边界，**不是额外本地网络跳数，也不提供 C++ 崩溃的进程隔离**。同机 HTTP/UDS sidecar 是后续可选方案；本轮不并行实现两套客户端适配。
28
29“干净”指自己维护的应用代码与变更边界，不是裁剪官方框架的全部通用能力。`RecommendEngine` 是固定流程的普通函数组合，不建设通用 DAG 平台或动态策略系统。
30
31业务目标仍是负载模型：真实特征读取、真实召回、真实 S/NS 前向和模型 KV 访问。OneTrans 采用显式发布的固定随机参数可接受，训练和准确率优化后置。模型输出同分可以接受，跳过前向后填同分不算执行完成。

46### 0.3 数据事实不随架构修订改变
47
48业务是 Tenrec QK-video 衍生 `ctr_data_1M` 固定快照的信息流推荐。入口保持 `POST /api/recommend`，业务场景 `home_feed`，profile `tenrec_load_v1`；以 `design_revision=2` 标明软件架构变化，不能误称数据/模型已重新发布。
49
50[真实样例证据](/root/half_latency/recommendation_design_assets/tenrec_sample_evidence.json) 来自前 200,000 数据行。uid=`1` 的首行历史有 10 项，样例目录中 9 项有视频类型编码，派生 `video_type_0=2/9`、`video_type_1=7/9`；类型缺失项保留缺失。这些覆盖和比例只描述该样例范围，不是全量统计。物品 `4`、`1201` 来自实际曝光行，用于接口输入说明，不声称是在线召回输出。
51
52`video_category` 表示**长/短视频类型，不是内容主题类目**；官方维护者在 [issue #11](https://github.com/yuangh-x/2022-NIPS-Tenrec/issues/11) 中确认了这一含义，但没有给出 0、1 分别对应长视频还是短视频。因此保留原始数值编码，不自行补命名。接口中的 `category_code` 仅为兼容字段名，语义固定为 `video_length_type`；词项使用 `video_type_0`、`video_type_1`。
53
54本地 CTR 文件为 20 列，QK/QB 视频原文件均为 10 列；其中 `item_id` 是物品标识，`video_category` 是上述粗属性，`click/like/follow/share/watching_times` 是交互记录，可按固定快照离线聚合，`age/gender` 属于用户特征。视频文件没有标题或标签，官方 [issue #14](https://github.com/yuangh-x/2022-NIPS-Tenrec/issues/14) 也未提供视频/内容链接。官方 CTR 生成程序保留原始 ID，因此可在核对实际数据版本后与 QK-video 关联，补充该版本已有的缺失字段或历史物品属性；这不会产生新的内容字段。Article 数据的 `category_first/category_second/item_score` 属于另一数据类型，不能仅凭同数字 ID 贴到 video 上。字段核对及后续统计见[数据审计](/root/half_latency/recommendation_design_assets/tenrec_audit/README.md)。
55
56历史按 `hist_1…10` 原顺序去零、保留重复，不追加目标点击；`positions=1…n` 是顺序编号。Tenrec 没有本方案可用的商品标题、库存、价格或艺术家/专辑，不为接口演示制造这些数据。缺少实际 DSSM 向量、SID 映射或分数时，样例保持待绑定并明确失败，不造随机值冒充运行产物。

114### 1.2 PaiRec 逻辑：自有 RecommendEngine
115
116```mermaid
117flowchart LR
118    C[自有 controller] --> V[固定请求 ID release deadline]
119    V --> U[FeatureRepository 读 USER 和 HISTORY]
120    U --> A[Dense Sparse Gen 并行]
121    U --> S[启动 S Future]
122    A --> F[融合 去重 已看过滤 限量]
123    F --> I[FeatureRepository 批读 ITEM_RANK]
124    I --> J[候选特征与 S 结果汇合]
125    S --> J
126    J --> N[ScoreClient 调用 NS]
127    N --> P[按首 logit 稳定后排]
128    P --> R[响应 执行状态 回收]
129```
130
131controller 负责请求校验、内部唯一 request_id、剩余总期限、HTTP 错误映射与响应。`RecommendEngine` 直接依赖业务接口，显式表达并行和等待；不借用 Recall 来触发 S，也不把真正精排藏在 Sort 插件中。
132
133源业务规则保留：Dense 50、Sparse 50、Gen 10；融合优先保留最多 10 个 Gen 候选，再按 Sparse/Dense 固定轮询补至最多 50。保留多来源，原始分数不相加；第二次 Redis 后不补拉。最终按 NS 第一个 logit 降序，依融合次序及原始 ID 稳定打破同分，最多返回 10 项。
134
135### 1.3 业务字段与模型状态的所有权
136
137| 数据 | 权威位置 | 谁在何时读取 | adapter 的职责 |
138|---|---|---|---|
139| 用户编码、`user_dense`、DSSM 用户向量、稀疏视频类型词项 | Redis USER | Engine 召回前，经过 FeatureRepository | 执行 MGET、保持 nil 位置、返回字节与错误；不自己建画像 |
140| 原始有序历史、positions、长度与 hash | Redis HISTORY | 与 USER 同次逻辑读取；生成/S/过滤共享 | 不自行改写历史或追加点击 |
141| 视频长短类型编码、候选 dense、缺失/有效计数 | Redis ITEM_RANK | 候选产生后按 ID 批读 | 不以本地 TSV 替代库访问 |
142| DSSM 物品向量与 ANN 索引 | Milvus | Dense 后端查询 | server adapter 只转协议，不代替 Milvus |
143| 真实物品词项与倒排索引 | OpenSearch | Sparse 后端查询 | server adapter 不伪造命中 |
144| OneTrans item/user/category embedding 与前端参数；category 表兼容槽使用视频长短类型编码 | PS/模型资产 | S/NS 内部按需 lookup | 保持模型参数路径，不经 PaiRec 每次搬整张表 |
145| 生成 engine/tokenizer/SID 表 | 模型资产；编码所需映射可随应用发布 | 启动装载、请求内进行 SID 适配 | 转换契约，不换另一套编码 |
146| S KV | DataSystem 精排 namespace | S 写、NS 读同一请求对象 | 完整传递身份；不主动制造额外 KV Get/Set |
147| TRT 原生 KV | DataSystem 生成 namespace | Executor 按其块生命周期处理 | 不把推荐结果缓存当原生 KV |
148
149DSSM 用户塔输出属于用户状态的派生结果，放 Redis；OneTrans user embedding 表属于模型参数，放 PS。两个“用户向量”不能按名称混同。静态快照仍经过规定的业务特征查询，才能覆盖目标数据库负载。

151### 1.4 Dense 服务逻辑
152
153```mermaid
154flowchart LR
155    U[Go DenseClient 业务请求] --> C[进程内 native client]
156    C -->|typed bRPC| A[Dense server adapter]
157    A -->|本机 POST /recall| D[向量维度与版本校验]
158    D --> M[(Milvus 实际 search)]
159    M --> R[原始 item_id score 本路次序]
160    R --> A
161```
162
163已有后端原来以 uid 查本地画像、运行用户塔；目标改为接收真实离线 `query_vector`。用户/物品向量由同 checkpoint、词表、归一化和快照生成；维度取实际配置，源码默认 64 不等于所有产物都是 64。
164
165在线 Dense 不再运行 user tower，不在正常路径加载本地全物品矩阵作 NumPy 回退。server adapter 的 protobuf 必须包含新向量契约，不能直接沿用旧 VectorRecall 的 uid-only 结构。该服务的真实在线负载为协议转换、向量传输、Milvus 检索与结果返回。
166
167### 1.5 Sparse 服务逻辑
168
169```mermaid
170flowchart LR
171    Q[Go SparseClient 兴趣词项] --> C[进程内 native client]
172    C -->|typed bRPC| A[Sparse server adapter]
173    A -->|本机 POST /recall| D[固定词项校验与查询 DSL]
174    D --> O[(OpenSearch BM25)]
175    O --> R[原始 item_id 分数 本路次序]
176    R --> A
177```
178
179`pairec_sh` 已有查询适配，尚无本目标独立薄服务。短期新增后端入口及 typed server adapter，装载真实 `video_type_<category_code>` 词项文档，其中 `category_code` 是兼容字段名，实际表示 `video_length_type`。mapping 固定 `tokens:text`、whitespace analyzer、BM25，`item_id:keyword`；index 由服务 manifest 绑定。
180
181用户词项来自同份 HISTORY 与实际 catalog 的视频长短类型关联、计数归一。unknown 不混入 `video_type_0`，空兴趣不造随机词项。正式 P0 保留这条二值类型词项的真实 BM25 链路；它验证服务联通及这种低选择性倒排访问的特定负载，不代表主题兴趣召回或文本搜索负载。0、1 的长短对应关系未知，不影响按原始编码匹配，但禁止将其解释成两个内容主题。

183### 1.6 生成召回逻辑
184
185```mermaid
186flowchart LR
187    H[同源 raw history] --> I[业务侧固定 SID 适配]
188    I --> C[进程内 native client]
189    C -->|现有 Recommend protobuf| G[Gen 原生 bRPC 服务]
190    G --> T[TRT Executor 实际推理]
191    T <-->|原生块换入换出| DS[(生成 KV)]
192    T --> P[合法 SID 与原始物品映射]
193    P --> R[候选 经 native adapter 返回]
194```
195
196Gen 直接复用现有 `RecommendService.Recommend`，不用远端 HTTP 桥。历史每项四层 SID，未知映射显式剔除；按实际 tokenizer/engine 输入容量保留完整项。现 proto 的候选 `item_id` 是 int32，发布检查必须验证范围，不能因其他服务用 int64 而忽略它。
197
198现有简化 SID 候选构造与常量分数可暂留，只要真实推理并返回合法 ID；不把它称为完整序列概率排序。adapter 不执行 semantic_map 假后端，不缓存推荐结果，不发 pressure Health，也不添加 KV probe 凑调用次数。

200### 1.7 OneTrans S 逻辑
201
202```mermaid
203flowchart LR
204    H[Go PrepareClient 历史与请求身份] --> C[进程内 native client]
205    C -->|typed bRPC| A[S server adapter]
206    A -->|本机 POST /ingest| S[历史 PS lookup 与 S CPU 前向]
207    S --> E[真实逐层 KV 与身份 envelope]
208    E --> DS[(共享 DataSystem)]
209    DS --> RD[写成功后 ready kv_key]
210    RD --> A
211```
212
213S 与候选无关，和三路召回并行。历史已经来自 Redis，不再用另一份 Kafka/JSON provider。当前 `/ingest` 的 HTTP 响应就在 `nearline.ingest()` 和 `store.put()` 之后；缺的是业务成功校验、请求身份、真实共享后端、错误传播与回收，不是重新发明写后响应。
214
215首期 S 固定 C++ CPU；模型固定随机参数可用，但 raw ID 到 PS 表必须真实命中或按明确 OOV 规则处理。左 padding 与 mask 属于模型形状，不能靠任意业务大包增加工作量。
216
217### 1.8 OneTrans NS 逻辑
218
219```mermaid
220flowchart LR
221    F[Go ScoreClient 完整特征与 kv_key] --> C[进程内 native client]
222    C -->|typed bRPC| A[NS server adapter]
223    A -->|本机 POST /score| FE[模型前端与 PS lookup]
224    FE --> N[真实 NS CPU 前向]
225    DS[(对应历史 KV)] --> V[验证 envelope 并反序列化]
226    V --> N
227    N --> R[同序 item_ids logits 执行状态]
228    R --> A
229```
230
231NS 不从本地 `user_features.tsv/item_rank_lookup.tsv` 自装配业务字段；保留 `/score` 的完整输入。`user_dense` 为两个原始编码加 13 个 reserved zero；`artist_ids=[category_code+1]` 是旧槽位中的视频长短类型编码适配，unknown=`[]`，`album_ids=[]`。此处 `category_code` 的语义是 `video_length_type`，`artist_ids` 不是作者或艺术家标识，不声称视频存在音乐元数据。
232
233首期 NS 固定 C++ CPU，真实执行两个输出头，PaiRec 取首 logit 排序，不称 pCTR。若改 CUDA 则建立单独 profile，不能静默回退。NS 的后续 attention 依赖用户 KV，不能把整个候选表示当成 item-only 离线向量。

235### 1.9 双侧 adapter 的边界
236
237| 层 | 做什么 | 不做什么 |
238|---|---|---|
239| Go 业务接口 | 表达 Dense/Sparse/Gen/S/NS/Feature 调用；携带版本和 deadline | 不编码 PRPC 帧、socket、bRPC service 元数据 |
240| CGO/C ABI | route 枚举、opaque handle、带长度 JSON buffer、剩余 timeout、状态和 trace | 不增加网络 hop；不让 C++ exception 穿过 ABI |
241| C++ client adapter | typed conversion、生成 stub、native Channel、连接复用、协议配置与取消 | 不编排三路、不查本地画像、不缓存推荐结果、不发压力流量 |
242| 四类 C++ server adapter | 原生 bRPC request → 本机既定 HTTP 后端；完整映射响应/错误/trace | 不把 HTTP 200 自动等同于业务执行完成；不引入 DeepFM 假契约 |
243| Gen 原生 server | 直接运行现有 Recommend 模型路径 | 不额外套通用 HTTP 桥 |
244| 模型内部依赖 | Dense→Milvus、Sparse→OS、S/NS→PS/DS、Gen→DS | 不因 client adapter 更换而自动换协议/设备 |

248## 2. 开发视图：新应用、契约与原生库
249
250### 2.1 干净应用接入官方 PaiRec
251

313### 2.4 ABI 与 protobuf 是两份不同边界
314
315**稳定 C ABI**控制 Go 与本地 C++ 的调用：固定 `rec_adapter_v1`、opaque client/request handle、route、JSON buffer 指针与长度、剩余 timeout、返回 buffer/error/trace，以及配对释放函数。输入在提交时复制到 C++ 所有内存，不把 Go 内存指针保留到异步生命周期。关闭 client 前排空在途调用，取消不能使正在访问的 buffer 提前释放。
316
317**typed protobuf**控制两台机器上 native client/server 的通信：Dense、Sparse、Prepare、Score 各有明确 request/response 类型，与五份既定 JSON 业务 payload 同义。Gen 复用现 proto。不能拿一个任意 URL＋任意 JSON 的通用代理替代服务契约，也不能借 payload padding 偷传版本字段。
318
319raw ID 在业务 JSON 中按既定字符串/int64 规则处理。C++ JSON 库和转换函数不得经过 double 再还原大整数。新增 protobuf 的 int64 范围与 Gen 的既有 int32 限制分别检查；protobuf JSON 的整数字符串规则要在显式转换层处理，不能盲用自动 JSON 转换后假设旧后端一定接受。
320
321| client route | 对外方法/协议 | 服务端处理 |
322|---|---|---|
323| `FeaturesMGet` | Redis RESP `MGET` | 直接 Redis，无新 Feature server |
324| `DenseRecall` | `loadmodel.v1.DenseRecallService.Recall` | Dense role → 本机 `/recall` |
325| `SparseRecall` | `loadmodel.v1.SparseRecallService.Recall` | Sparse role → 本机 `/recall` |
326| `GenerativeRecall` | `pairec.inference.RecommendService.Recommend` | Gen 原生终结 |
327| `PrepareHistory` | `loadmodel.v1.HistoryPrepareService.Prepare` | Prepare role → 本机 `/ingest` |
328| `ScoreCandidates` | `loadmodel.v1.CandidateScoreService.Score` | Score role → 本机 `/score` |
329| `ReleaseHistory` | `loadmodel.v1.HistoryPrepareService.Release` | Prepare role → 新增管理入口，幂等释放；不是模型阶段 |

331### 2.5 哪些变化影响哪一层
332
333| 变化 | 主要修改 | 需验证但不自动重写的层 |
334|---|---|---|
335| 召回预算、融合/后排规则、特征读取顺序 | Go Engine 与业务配置 | adapter 只透传合法参数；模型协议不变则不需改 server |
336| 字段、shape、业务语义变化 | 业务 DTO/schema、protobuf、双侧转换、相关后端 | 必须跨层共同版本，不能靠 ABI 稳定掩盖业务契约变化 |
337| bRPC 连接策略、实现升级、TCP/后续 UB profile | native client/server、构建与部署绑定 | Go Engine 不写传输实现；仍需端到端兼容和实际数据面验证 |
338| backend 的纯 wire 兼容实现优化 | 对应模型服务或 server adapter | 不必然修改 Go；不能笼统说每次服务端升级都要改调用方 |
339| 原生 ABI/链接依赖变化 | native binding、构建与发布 | 静态链接或 ABI 不兼容时可能重编应用，不能承诺总能只换 `.so` |
340| 特征快照或模型版本更换 | ETL、manifest、模型/索引装载、就绪门禁 | DTO不变时可复用业务代码，但版本/覆盖必须重新验收 |
341
342### 2.6 旧工程不导入什么
343
344DeepFM、Go PRPC framing、burst/reverse burst、pressure hop、Health 扇出、旧 controller/sort/latch、vendor patch 不进入新应用树，因此无需先从 8506 大量删除文件才能建立新应用。已有真实模型端仍可能含实验后端、结果缓存或压力开关，必须在服务发布配置中关闭；应用干净不能替模型端保证执行真实性。
345
346模型库、SID/向量导出、DataSystem SDK、PS、trace 中有用的测量语义可按职责复用。历史运行脚本不直接成为新部署清单，避免把实验拓扑一并启动。

458### 3.3 并发与资源责任
459
460| 组件 | 状态与并发 | 必须保证 |
461|---|---|---|
462| Controller/Engine | 每请求 immutable 特征、独立候选结果、S Future、deadline | 不让多个 goroutine 无锁改同一 map；有界扇出；无隐藏重试 |
463| Native client | 按 route/目标复用 Channel；每调用独立 Controller/response | 不因一个 singleton 或总锁串行化五服务；无全局多目标串用 |
464| CGO binding | 调用可能阻塞 OS 线程，Go context 不自动取消 C++ | 传播剩余 timeout；可取消调用有明确 request handle；buffer 只在使用完毕后释放 |
465| Server adapter | 对应角色的有界并发与本机 HTTP 连接池 | 不以单线程桥接制造额外串行瓶颈；保留后端错误 |
466| Dense/Sparse | 索引连接及后端查询 | 真实外部查询，不替换为本地结果缓存 |
467| Gen | GPU/Executor 调度与原生 KV | 正常批处理可保留；不额外发压力 lane |
468| S | PS 查询、CPU 计算、KV 写入 | 成功后 ready；失败/拒绝/取消均有状态 |
469| NS | PS 查询、KV 读取、前向；可批处理 | 每请求候选/身份/KV 对应；首期固定 cpp_cpu |
470
471native C++ 崩溃会影响同一 PaiRec 进程，CGO 只隔离代码和协议依赖。若未来需要故障进程隔离，才改用 sidecar；该变化增加进程和本地 RPC，必须成为独立测量配置。
472
473### 3.4 请求级 KV 与取消状态机
474
475目标 key 为 `fine:<release_id>:<model_version>:<request_id>`。request_id 内部生成唯一，外部调用 ID 默认只用于关联。实际存储 envelope 包含 release/model/request/user/history 身份及层数、长度、dtype；只在 JSON 或内存 Record 添加字段，不能保证跨进程可验证。
476
477```mermaid
478stateDiagram-v2
479    [*] --> Pending: 已取得同源历史
480    Pending --> Running: S 实际开始
481    Pending --> Failed: 拒绝或输入错误
482    Running --> Ready: S完成且KV写成功
483    Running --> Failed: PS计算存储失败
484    Running --> Cancelled: 请求取消或到期
485    Ready --> Scoring: NS校验同一身份
486    Ready --> Reclaim: 上游已取消
487    Scoring --> Completed: NS真实前向完成
488    Scoring --> Failed: KV失效或计算失败
489    Completed --> Reclaim
490    Failed --> Reclaim
491    Cancelled --> Reclaim: 在途任务结束后清理
492    Reclaim --> [*]: 删除或受控过期
493```
494
495OneTrans [DataSystem adapter](/root/real_model/OneTrans_HSE_project/cpp/src/kv/datasystem_store.cpp:46) 已有 `SetParam.ttlSecond`、`Del`、`Expire`；默认 TTL 为 0。正式配置以 TTL=120 秒、`cleanup_owner=pairec_request` 为联调初值，需要验证覆盖最坏处理窗口。
496
497Engine 在 S Future 明确成功后首次调用 NS。KV miss、损坏 payload、版本不符、存储不可用分别报错；不能跳算返回 0.5 成功。取消不代表下游已停止；完成回调处理迟到写入，独立有界管理调用删除已结束对象，TTL 兜底。native adapter 转发状态，不自行猜测对象是否无人使用；新 `/release` 校验本请求 owner，迟到写通过模型端状态与回收逻辑处理。
498
499### 3.5 期限与失败
500
501请求总 deadline 为 **25 秒**，早于官方 HTTP server 的 30 秒读/写超时，留出错误返回和响应序列化时间。证据：[app.go](/root/half_latency/recommendation_design_assets/source_pairec_upstream_v2.6.2/app.go:82)。Redis 每逻辑阶段预算 1 秒，Dense/Sparse 各 5 秒，Gen/S/NS 各 10 秒；每次 ABI、native RPC、本机 HTTP 均取阶段预算和剩余总预算的较小值，不在每层重新获得完整超时。
502
503这些是接线初值，不是性能目标。首期自动 retry=0；连接失败、参数/版本错误和真实模型未执行均不能算完整成功。ITEM_RANK 整键 nil 采用 `drop_and_report` 且不补拉，坏 JSON、错版本或 transport 错误仍 strict 失败。实际候选不足只返回实际数和 shortfall，不造物品补满。

582### 4.2 各边实际协议
583
584| 边 | 当前目标 | 不可误报 |
585|---|---|---|
586| 用户→PaiRec | HTTP | 不称全链无 HTTP |
587| Go→native client | CGO/C ABI，同进程 | 不计算为本地 RPC；也不称零开销 |
588| native client→Dense/Sparse/S/NS adapter | 生成 protobuf + 原生 bRPC baidu_std/TCP | 不是 Go 手写 TCP wire |
589| server adapter→模型后端 | 本机 HTTP | 桥接成本真实存在，不算纯网络时延 |
590| native client→Gen | 现有原生 Recommend bRPC/TCP | 不再套冗余 HTTP 桥 |
591| native client→Redis | bRPC 库 `PROTOCOL_REDIS`，RESP/TCP | Redis 不支持 baidu_std；使用 bRPC 库不等于支持 UB |
592| Dense→Milvus | 所选 Milvus SDK 的真实协议 | 不自动变成 bRPC |
593| Sparse→OpenSearch | HTTP 查询 | 不自动变成 bRPC |
594| S/NS→PS | 现有 native bRPC 参数查询 | 不等于业务特征 Redis |
595| 模型→DataSystem | 各自实际 C++ SDK 路径 | 生成与精排 KV 格式和生命周期不同 |
596
597先完成 TCP 基线，再另建 UB profile。切换传输需要客户端与服务端匹配构建、运行库和实际数据面验证；不允许静默 TCP 回退后仍记为 UB。旧 UB gateway 的转发经验可参考，但其压力分支、按前端连接建 lane 等实验行为不进入默认新应用。

599### 4.3 物料、资源和后端固定
600
601| 角色 | 必备物料/状态 | 就绪判据 |
602|---|---|---|
603| PaiRec 新应用 | 官方锁定依赖、自有业务代码、ABI匹配的native库、渲染后配置 | route 确实进入新 controller；实际 native 库/协议和发布一致 |
604| native client | brpc/protobuf/运行库、目标 route 与连接配置 | ABI版本与依赖完整；无额外 sidecar；正确连接各类后端 |
605| 四类 server adapter | 新 typed protobuf、role 与本机 backend URL | 匹配客户端 schema；能识别后端业务 readiness |
606| Dense | 已加载目标 Milvus collection；向量空间元数据 | 真 search；失败不退本地 NumPy |
607| Sparse | 已装载文档、固定 mapping/index | 实际 BM25 查询；不是仅进程可达 |
608| Gen | engine/tokenizer/SID/目录、兼容 TRT/DataSystem 运行库、GPU | 实际 runner；禁 semantic_map/结果缓存/压力 probe |
609| S/NS | 相同 OneTrans 资产、PS 表、DataSystem | `cpp_cpu` 实际后端；模型、schema、raw ID覆盖一致 |

615### 4.4 启动与恢复
616
617```mermaid
618flowchart LR
619    A[锁定数据及模型发布] --> B[构建新应用与双侧native适配]
620    B --> C[启动数据库并装载校验]
621    C --> D[启动五服务和各server adapter]
622    D --> E[原生通信与单服务真实执行检查]
623    E --> F[自有controller与Engine就绪]
624    F --> G[一条真实用户请求]
625    G --> H[有界多用户回放与回收检查]
626```
627
628恢复按实际状态分别处理：Redis/Milvus/OpenSearch 使用持久化或版本化重装；PS 重启后重新装表；S KV 可以丢弃并按新请求重建。模型服务的 health、server adapter 的可达、native client 的连接成功三者都不能单独证明整个角色就绪。
629
630原生库发布需要固定 ABI、编译器/运行库、brpc/protobuf 等兼容性。readiness 报告实际加载的 adapter、libbrpc、protobuf 和 transport 构建标识，并核对 runtime manifest，不能只打印配置里期待的版本。底层通信变化时，native client 与对应 server 双端匹配验证。
631
632动态库替换只有在 ABI与依赖兼容时才可能不重编 Go；静态链接或 ABI 改动仍可能重编整个应用。新架构减少通信实现散落，不能消除所有构建与联调工作。

636## 5. +1 场景视图：检验四个视图是否一致
637
638### UC-01 干净启动与路径选择
639
640**步骤**：从官方 v2.6.2 依赖构建新应用和 native 库；公开 hook 注册自有 controller；加载 design_revision=2 的正式配置；检查 route、ABI、schema、release、后端 readiness。
641
642**证据**：业务 trace 明确来自新 Engine；构建清单不含8506的Go wire/DeepFM/压力对象；四个旧框架配置为空不会导致请求进入旧默认 UserRecommend。源码锁定证明来自官方，不把旧 vendor 副本标作干净基线。
643
644### UC-02 离线加工与人工装载
645
646**步骤**：统一真实用户/历史/catalog/物品统计 → DSSM两塔离线导出 → 视频长短类型词项文档 → SID/OneTrans/PS资产检查 → Redis/Milvus/OS/PS装载 → 数量、维度、版本、覆盖和样本读回 → 标记完整release可用。
647
648**证据**：真实产物清单、装载计数和缺失比例。fixture不是全量release；不会静默裁成微小交集再称全规模。此步骤不依赖OneTrans训练。
649
650### UC-03 一次完整推荐请求
651
652**前提**：选择本release里真实、历史有效、向量和SID资产可用的用户。样例uid1只证明字段来源，不能代替模型资产就绪。
653
654**步骤**：按3.1执行，首轮Redis→三召回与S→融合→候选Redis→等待S成功→NS→后排。
655
656**证据**：同request/release对应两次特征读、三路实际后端、S PS/forward/Set、NS Get/forward和最终列表。native client/server trace与后端trace可关联。固定完整验收的候选特征nil数要求0；不要求准确分数或所有分数不同。
657
658### UC-04 冷KV与跨进程消费
659
660**步骤**：确保请求key不存在；S实际计算并写；ready经server/client adapter完整回传；NS读同key与envelope后真实前向。
661
662**失败变体**：写成功后删除对象或注入错误版本；NS明确KV缺失/版本错误，不返回填充logits成功。验证adapter不会把业务错误转换为成功HTTP/成功bRPC。
663
664### UC-05 同uid并发与资源所有权
665
666**步骤**：同uid两个内部request_id并发，S故意乱序完成；各NS只读各自key；一个完成清理不影响另一个。
667
668**证据**：没有旧`model/user`覆盖；native client可并行不同route；无全局串行锁；C ABI输出buffer各归本调用，无交叉释放。重复外部调用标识不造成KV键碰撞。
669
670### UC-06 超时、取消与迟到写
671
672**步骤**：延迟真实S/存储或中断连接；Engine按25秒总期限及阶段预算失败；native取消或超时向下传播；仍在途S结束后回调/TTL回收。
673
674**证据**：每层使用剩余期限，不因桥接重新起算；无隐藏重试；取消不提前释放还在被C++使用的内存；迟到KV不会永久增长。S失败时NS不运行，不能被计为五阶段成功。
675
676### UC-07 输入缺失与候选不足
677
678| 情况 | 正式结果 | 检查重点 |
679|---|---|---|
680| USER/HISTORY键不存在 | 明确特征未就绪/未知用户 | 不用本地业务表回退 |
681| 向量维度/空间错误 | 显式拒绝 | 不造64维向量替代 |
682| 稀疏兴趣为空 | empty，说明未发生查询或返回零结果 | 不造词项；不作为五服务贯通样本 |
683| 召回后端失败 | strict失败 | adapter保留原始错误，不返回空数组冒充成功 |
684| Gen候选较少 | 实际数量与shortfall | 不造SID/候选；保留token数 |
685| ITEM_RANK整键nil | drop_and_report，不补拉 | MGET位置不能错位 |
686| ITEM_RANK坏JSON/错版本 | strict失败 | 不当作普通nil丢弃 |
687| PS miss/OOV | 明确模型规则或失败 | 不把全零参数供给计为正常覆盖 |
688
689### UC-08 版本或ABI不匹配
690
691**步骤**：分别替换错误schema、模型/历史envelope、protobuf、native ABI版本或运行库。
692
693**期望**：可在启动发现的拒绝ready；请求层版本不一致明确报错；未知路由不落到默认模型。大整数ID完成Go→C++→protobuf→后端→返回的无损对照，Gen int32越界明确拒绝。
694
695### UC-09 服务重启与桥接失败
696
697**步骤**：分别重启native库所属的PaiRec进程、某server adapter、模型后端或存储；检查旧连接与inflight状态；完成就绪和装载后重跑真实请求。
698
699**证据**：server adapter活着但模型未ready时不能放流；PS重启明确重装；DataSystem丢失KV不读取旧用户对象。CGO下native崩溃使PaiRec一起退出是既定故障边界，不伪称进程隔离。
700
701### UC-10 通信替换与持续负载
702
703**TCP基线**：用同一业务数据、模型shape、候选预算和设备，外部回放产生用户请求；记录业务执行率、adapter转换、native RPC、模型计算、排队、Redis和KV生命周期。
704
705**后续传输profile**：若采用UB或sidecar，各自改变对应层并单独验收；UB确认双端实际数据面且不静默fallback；sidecar记录新增本地RPC/进程成本。它们不是默认profile的无痕升级。
706
707**完成证据**：长期对象数量、在途请求和内存可解释；没有内部burst/Health放大；每条RPC及实际backend可关联。不能用两个包络相减直接宣称纯网络延迟，也不能把并行阶段时间相加等同端到端时延。
