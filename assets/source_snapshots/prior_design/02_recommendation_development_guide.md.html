30### 1.2 官方扩展点足以承载自有 Controller
31
32上游 [Run](/root/half_latency/recommendation_design_assets/source_pairec_upstream_v2.6.2/pairec.go:74) 先加载 `-config` 指定文件，随后注册默认路由，再运行 start hooks；[HandleFunc](/root/half_latency/recommendation_design_assets/source_pairec_upstream_v2.6.2/route.go:56) 调用路由表注册，而 [Register](/root/half_latency/recommendation_design_assets/source_pairec_upstream_v2.6.2/controller.go:66) 按 path 覆盖。因此可在自有 `AddStartHook` 中绑定 `/api/recommend` 的 handler，不修改上游框架。
33
34```go
35// 【新增设计】cmd/pairec-loadmodel/main.go，错误处理示意。
36func main() {
37    pairec.AddStartHook(func() error {
38        cfg, err := DecodeStrictLoadModelConfig(recconf.Config.UserDefineConfs)
39        if err != nil { return err }
40        release, err := ReadAndValidateReadyRelease(cfg)
41        if err != nil { return err }
42        native, err := OpenAndVerifyNativeAdapter(cfg.Transport, release)
43        if err != nil { return err }
44        engine, err := NewRecommendEngine(cfg, release, NewTypedClients(native))
45        if err != nil { native.Close(); return err }
46        handler := NewRecommendController(engine) // 保持明确所有权与关闭顺序
47        pairec.HandleFunc("/api/recommend", handler.ServeHTTP)
48        RegisterOwnedShutdown(engine, native)
49        return nil
50    })
51    pairec.Run()  // 启动前用 renderer 生成 -config 对应的正式文件
52}
53```
54
55使用 `HandleFunc` 绑定持有 engine 的方法；不要依赖上游按反射复制 controller 时隐含保留未导出成员。上游 [runStartHook](/root/half_latency/recommendation_design_assets/source_pairec_upstream_v2.6.2/pairec.go:130) 对 hook 返回错误执行 `panic(err)`，不是日志后继续；自有 hook 必须真正返回 manifest、native 初始化、数据库 readiness 等错误。不要在构造器内部吞错再返回空对象。
56
57正式配置的 `SceneConfs/UserFeatureConfs/FeatureConfs/RecallConfs/SortConfs` 等保持空，自有 Engine 显式调用各阶段。没有 `LoadModelRecall`、UserFeature callback 或 Sort 承担远端模型调用，也不修改上游 `UserRecommend`。上游 HTTP [读写超时](/root/half_latency/recommendation_design_assets/source_pairec_upstream_v2.6.2/app.go:82) 固定为 30 秒；本次 engine 总预算设 25,000ms，保留序列化与返回窗口。预算是联调上限，不是性能目标；子阶段用 `min(stage_budget, remaining_deadline)`，不能各自重新获得完整请求预算。未来若确有超过 30 秒的产品需求，再另行评估自有 HTTP server，不在 hook 中写一个随后会被覆盖的超时字段。

116### 3.2 C ABI 的最小完整合同
117
118【新增设计】ABI 名称 `rec_adapter_v1`，采用 opaque handle＋显式长度 UTF-8 JSON。JSON 是进程内稳定业务边界，不是自定义远端 wire；C++ 解析后填 generated typed protobuf。头文件只暴露固定宽度整数、字节指针和结构大小；不暴露 STL、C++ exception 或 protobuf 类。
119
120```c
121/* 伪接口。枚举/结构布局在第一次实现时锁定并增加 ABI 契约测试。 */
122typedef struct rec_client rec_client;
123typedef struct rec_call rec_call;
124typedef struct { uint8_t* data; size_t len; } rec_owned_buffer;
125
126int rec_client_create_v1(const uint8_t* config, size_t len, rec_client** out);
127int rec_call_submit_v1(rec_client*, uint32_t route,
128                      const uint8_t* request, size_t request_len,
129                      uint32_t remaining_timeout_ms, rec_call** out);
130int rec_call_wait_v1(rec_call*, uint32_t wait_slice_ms, rec_owned_buffer* result);
131int rec_call_cancel_v1(rec_call*);     /* 幂等；不保证远端已停止执行 */
132void rec_call_release_v1(rec_call*);   /* 释放调用方引用，不直接杀死callback对象 */
133void rec_buffer_free_v1(rec_owned_buffer*);
134int rec_client_close_v1(rec_client*, uint32_t grace_ms);
135int rec_client_destroy_v1(rec_client*); /* 只有关闭且引用已排空才成功 */
136```
137
138| 项目 | 必须实现的规则 |
139|---|---|
140| 初始化 | 校验 ABI version/struct_size、配置、生成代码及 native 依赖版本；失败返回明确错误，不启动空客户端；输出实际 build info |
141| 输入所有权 | `submit` 返回前完整复制传入字节；异步期间不得保存 Go 指针。Go 使用固定类型 JSON 编码，不经 `map[string]interface{}` 的 float64 绕行 |
142| 输出所有权 | `wait` 返回终态时至多一次转移 buffer；明确 `PENDING/OK/ERROR/CANCELLED`，错误体也有长度。buffer 只由 `rec_buffer_free_v1` 释放，不跨 allocator 用另一份 `free` |
143| 异常 | 每个 extern-C 边界捕获 C++ exception，转换 bounded error。状态明确区分参数、排队满、超时、取消、网络、后端、业务校验，不能都视为无候选 |
144| 有界资源 | 限制总在途、排队数、请求/响应字节、单批 key 数；满则立即 `OVERLOADED`。终态但尚未释放的 call/result 也占用资源额度，防慢消费者耗尽内存 |
145| deadline | 提交时把 remaining 转成 native monotonic deadline；排队耗时扣预算，RPC timeout 使用剩余值；过期任务不继续发出。backend HTTP bridge 同样传递剩余预算 |
146| 等待 | Go 包装器用短 `wait` slice（例如 ≤50ms）配合 context；不为每个 RPC额外起一个永远阻塞的 goroutine。cgo waiting/转换时间记录为真实开销 |
147| 取消 | `cancel` 设置状态并尽力调用所选 native 库的取消能力；与完成竞争时只发布一个终态。远端可能已执行，需要独立释放控制和有限 TTL，不用取消作为“未执行”证据 |
148| callback 生命周期 | call 使用 native 引用计数；Go release 只减调用方引用，排队任务/正在执行的 RPC callback 持有自身引用，终态后释放，避免 use-after-free |
149| 关闭 | `close` 原子进入 CLOSING，拒绝新提交，取消未开始任务，等待正在进行回调至 grace。超时返回 BUSY 并保留对象；不得假装关闭成功后释放仍在使用的 Channel |
150| 销毁 | 只有 client/call/buffer 引用全部排空才 destroy；不在调用或 buffer 存活时卸载动态库。业务请求停止接入→engine排空/取消→控制回收→adapter close/destroy |
151| 线程与鉴权 | native 内维护受控 worker/Channel，禁止每次新建连接；敏感凭据仅配置解析使用，不回传 trace。热更新用新 client 完成健康检查后替换，旧实例排空 |
152
153此方案隔离代码与传输依赖，**不隔离 C++ 崩溃**：native 在 PaiRec 进程内运行。JSON/cgo 消耗应单独观测。future sidecar/UDS 可以作为故障隔离选择，但会增加进程与调用跳数，本轮不同时实现两套。

155### 3.3 Typed codec 不能盲用 protobuf JSON
156
157【现有风险】旧 bridge 的 `MessageToJsonString` 可能把 protobuf int64 输出为 JSON 字符串；OneTrans [parse_score_input](/root/real_model/OneTrans_HSE_project/cpp/src/serving/json_io.cpp:23) 使用 `as_int()`，其 [JSON 值实现](/root/real_model/OneTrans_HSE_project/cpp/src/common/json.h:57) 对错误类型缺少严格检查，可能把字符串 ID 当成 0。不能把旧 bridge 的通用转换原样套在新 S/NS 上。
158
159【新增设计】两个边界都用显式 codec：Go business JSON→native typed request；服务端 protobuf→既有 HTTP JSON。外部 raw ID 按契约保留十进制字符串，OneTrans 输入 `uid_sparse/item_id/artist_ids` 为经范围检查的 JSON 数字；响应候选 ID 按样例输出字符串。版本、历史 hash、候选顺序与空数组完整保留，未知字段/不匹配类型拒绝。生成召回历史 SID 是 int32[4]，输出 item_id 的 int32 上限需要发布检查。
160
161当前 OneTrans 自有 JSON parser 用 double 存数字，仅换一个 `as_int64` 函数名不足以支持全范围 int64。首版可以**显式验证实际 Tenrec ID 在精确整数范围内**；若宣称通用 int64 支持，就必须让 parser 原生保存/解析整数。native codec 本身必须使用保精度的整数解析，不以 double 中转。
162
163桥接请求必须保持 request_id、剩余 deadline、版本和实际 backend；HTTP 非2xx、坏 JSON、`accepted=false`、`executed=false` 或 shape/ID 不符均是明确错误。HTTP transport 成功不等于模型完成。适配器不得补候选、补特征、补 logits 或制造成功 trace。
164
165### 3.4 构建与更新范围
166
167发布物包含 native client library、四种 server role、generated protobuf、Go 二进制、C ABI 版本、native bRPC/protobuf/编译器依赖与运行时库清单。Go 只在 `internal/transport/native/cgo.go` 引入头文件与 link flags；CI 必须构建最终 Go 目标并验证运行时装载，不能只做 Go 类型检查。
168
169native 库变更主要集中在 adapter 的构建和部署；静态链接或 ABI/运行库变化仍可能要求重编 PaiRec 与 bridge 并联调，不能承诺“永远只换一个 .so”。wire 兼容的服务端更新通常不要求 Go 改业务类型；业务字段语义改变仍需统一合同迁移。
170
171先完成 TCP 基线。将来测试 UB 等 transport 时，要验证调用两端和对应协议实际支持并记录生效路径，禁静默 TCP fallback。Redis 用 native bRPC client 库发送 RESP，不意味着原生 Redis 具备 UB 协议能力；Milvus SDK、OpenSearch HTTP、PS native BRPC、DataSystem SDK 也各有独立边界，不能因为顶层 adapter 统一就声称全链路传输已统一。

564### 7.3 回收闭环与 Release 控制
565
566逻辑所有者是 PaiRec 请求，物理删除由 OneTrans S/NS 的 DataSystem adapter 执行。现有 DataSystem 实现 **已经提供** put TTL、del、ttl/Expire，分别在第46、70、81行；缺口是接入 request lifecycle 和错误传播，不能描述成完全没有 TTL 能力。模板 `kv_ttl_seconds=120` 是有限联调初值，需覆盖最大真实执行窗口，后续以运行证据调整。
567
568【新增设计】S 的 `/release` 控制端点接受完整身份与 kv_key，验证归属后幂等执行；server adapter 只桥接此入口，不越过模型服务直接操作 DataSystem。除已存在 key 的 Del 外，还需在 S 请求管理器中登记 canceled/closed key：若 Prepare 尚在执行，完成 Set 后检查登记并再次 Del；若 Release 先于 Prepare 到达，Prepare 开始前/Set后也检查登记。登记有界、生命周期覆盖允许的最迟请求完成窗口；拒绝重用已关闭 request_id。P0 不需要单独做通用回收服务。
569
570正常顺序是 S Set→ready→NS Get/forward→NS 完成释放；PaiRec 的 Release 作为幂等补充。NS未启动或已经确认终态可立即删；NS已发出但取消后状态未知时，登记 release_pending，不能因Go context取消就推断远端结束或删除仍有读者的对象。等待NS服务终态删除/确认，无法确认则由覆盖最大执行窗口的TTL兜底；不在P0额外构建跨服务读者租约平台。召回失败、空候选、第二阶段特征失败、NS无法发起、超时取消均在 finally 安排 Release。取消不保证远端停止；响应已丢失时不能依赖 Go 得知晚到成功，依靠 S 请求状态和 TTL 收尾。一次过早 Del 之后就忘记请求会漏掉随后 Set。
571
572清理使用独立、有界的管理 context，模板初值1,000ms；不继承已过期的业务context导致Release永远无法发出。清理并发/队列也必须有界，管理流量与延迟单独计量，失败留可见状态与TTL兜底，不阻塞业务返回无限重试。
573
574request状态与 native call 状态分开：native RPC可以早于模型计算结束而取消，本请求资源仍需要生命周期处理。禁止自动重试推理，避免相同key两个producer互相覆盖；未来重试需定义 attempt/幂等策略。回收日志记录 scheduled/completed/failed/expired，排空后检查 KV 数量/字节趋于有界。Gen KV 沿 TRT 自身生命周期，不套用这套 OneTrans key 删除方案。

596### 8.2 完整伪代码
597
598```go
599func (e *RecommendEngine) Recommend(parent, request) (Response, error) {
600    req, err := ValidateAndAssignUniqueRequestID(request)
601    if err != nil { return ErrorResponse(err) }
602    ctx, cancel := WithDeadlineWithinParent(parent, 25*time.Second)
603    defer cancel()
604    release := e.PinReadyRelease() // 请求内不可变化
605    lifecycle := NewRequestLifecycle(req.ID, release, e.ReleaseControl, cleanupBudget=1*time.Second)
606    defer lifecycle.Finalize()    // 所有return/panic路径都安排必要回收
607    defer FinishTrace(lifecycle)
608
609    features, err := e.Features.LoadRequest(ctx, release, req.UID) // 第1阶段
610    if err != nil { return StageError("feature_preload", err) }
611    lifecycle.SetImmutableFeatures(features)
612    prepare := StartPrepare(ctx, lifecycle, features, e.Clients)
613    // 三个客户端和Prepare各仅启动一次；每个native调用都受有界资源与剩余预算约束。
614    recalls, err := RunThreeRecalls(ctx, features, release, e.Clients)
615    if err != nil { return StageError("recall", err) }
616    candidates := Fuse(recalls, features.History, e.Config.Fusion)
617    if len(candidates) == 0 { return EmptyResponseWithStageStatus(lifecycle) }
618
619    itemFeatures, err := e.Features.LoadCandidates(ctx, release, candidates) // 第2阶段
620    if err != nil { return StageError("candidate_features", err) }
621    candidates = RemoveReportedMissingIDs(candidates, itemFeatures.Dropped)
622    if len(candidates) == 0 { return EmptyResponseWithStageStatus(lifecycle) }
623    ready, err := prepare.Wait(ctx)
624    if err != nil { return StageError("prepare", err) }
625    RequireReadyIdentityAndBackend(ready, lifecycle.Identity)
626
627    payload := BuildScoreRequest(req, features, candidates, itemFeatures, ready)
628    lifecycle.MarkScoreSubmitted() // 超时但终态未知时禁止立即删除可能仍被消费的KV
629    scores, err := e.Score.Score(ctx, payload) // 经native CGO→BRPC→NS服务端桥→/score
630    if err != nil { return StageError("score", err) }
631    if err = ValidateScores(scores, payload, release); err != nil {
632        return StageError("score_contract", err)
633    }
634    scored := AttachFirstLogitScores(candidates, scores)
635    final := StablePostSortAndTopK(scored, req.Size)
636    lifecycle.MarkLastConsumerCompleted(ready.KVKey)
637    lifecycle.ScheduleRelease(ready.KVKey)
638    return SuccessWithActualCounts(final, lifecycle.Stages()), nil
639}
640```
641
642伪代码中的 `Require*` 实现要返回可处理 error，不能放任 panic 把可诊断的接口错误变成通用500。终态 stage 分为 completed/failed/cancelled/skipped，空候选可以业务合法，但不算“五阶段均实际执行”的贯通验收。strict 配置任一必需阶段错误返回具体 stage/code，不能只打印日志后给正常成功；一般推荐业务的降级策略后置为另一显式 profile。
643
644并发状态用各阶段独立结果槽/Future及受保护的 lifecycle，禁止多个 goroutine 直接改普通 map。RequestFeatures 冻结后只读。RunThreeRecalls 在任一路失败后取消/排空本次其他在途调用，不能遗留 goroutine/句柄；不要用会顺带取消整个父ctx的局部 errgroup 导致仍需要的 Prepare 失效。Prepare 的失败应可及时通知父请求并取消后续工作；返回前回收安排不要求把整个剩余 deadline 耗尽。
645
646controller 使用标准 net/http request context，严格限制 body/uid/size/scene，统一错误映射；request_id 在请求生命周期内唯一并经过字符/长度校验。客户端重复传同ID不得静默覆盖另一个在途请求的KV；首版可拒绝冲突，或服务端生成唯一实际ID并把外部ID仅作为关联字段。所有引用同一实际ID并回显。
