21### 0.5.1 推荐业务概念（推荐管线各 stage）
22
23推荐服务把"为用户选 N 个物品"拆成一条管线，按执行顺序：
24
25| 术语 | 译名/含义 | 在 pairec 里的角色 | 锚点 |
26|---|---|---|---|
27| **召回 (recall)** | 从海量候选(百万级)粗选出数百~数千个候选 item | 管线第 1 段；多路并发(热门/协同过滤/向量等)，每路返回一批 item 后合并 | `service/recall.go:54` |
28| **过滤 (filter)** | 去重、去已曝光、去黑名单、多样性约束等 | 管线第 2 段；按 scene 查注册的 filter 链顺序执行 | `filter/filter.go:70` |
29| **粗排 / 粗排 (general rank)** | 用轻量模型对召回的数千 item 打分、裁剪到数百 | 管线第 3 段；`GeneralRankService` | `service/general_rank/general_rank.go:216` |
30| **特征装配 (feature)** | 给每个 item 拉取/计算模型所需特征(用户特征、item 特征、交叉特征) | 管线第 4 段；隐藏的 I/O 长杆，DAO fan-out 取数 | `service/feature/feature_service.go:77` |
31| **精排 (rank)** | 用重模型(如 EAS 深度模型)对数百 item 精细打分，写回 `item.Score` | 管线第 5 段；两级 goroutine 嵌套并发调 EAS | `service/rank/rank_service.go:102` |
32| **冷启排 (cold start rank)** | 对新 item/新用户的专门打分策略(冷启动 = 历史数据不足) | 管线第 6 段；**仅 pipeline 路径有**，主路径无 | `service/rank/cold_start_rank.go:14` |
33| **重排 (sort)** | 在已有精排分数上做最终排序：去重、多样性、流量控制、业务规则 | 管线末段；DPP/SSD/ItemScore 等多种 sort 串行 | `sort/sort.go:65` |

51### 0.5.3 并发与 OS 概念
52
53| 术语 | 含义 |
54|---|---|
55| **stage** | 管线的一段（召回/过滤/.../重排各是一个 stage）。 |
56| **G0 / G-pipe / G-recall 等** | 本文档对 goroutine 的记号：G0 = 主请求 goroutine，G-pipe = pipeline 路径 goroutine，G-recall = 召回扇出的子 goroutine。Go 原生词是 goroutine（用户态轻量线程，M:N 调度到 OS 线程）。 |
57| **GMP** | Go 运行时调度模型：G(goroutine) M(OS 线程) P(调度器，容量=GOMAXPROCS)。网络 I/O 经 netpoller，G 阻塞时解绑 M 不膨胀线程；仅阻塞 syscall/文件 I/O 才占 M。详见 §3.2。 |
58| **GOMAXPROCS** | P 的数量上限 = 可同时跑 CPU 的 goroutine 数。pairec 用 `automaxprocs` 按容器 CPU 配额自动设。 |
59| **netpoller** | Go runtime 的网络 I/O 等待机制，底层在 Linux 用 epoll。goroutine 等网络数据时**解绑 M 挂到 netpoller，不占线程**——这是 pairec M(线程)数不随 QPS 膨胀的根因。详见 §3.2。 |
60| **epoll** | Linux I/O 多路复用机制。一个线程用 epoll_wait 同时监听大量 fd，谁就绪返回谁。netpoller 即基于 epoll，pairec 4 万个 G 等网络响应实际只有少量 M 在轮询 epoll。 |
61| **futex** | Linux "fast user-space mutex"，用户态快速互斥/等待原语。channel 和 sync.WaitGroup 的等待/唤醒底层用 atomic + futex wake，走纯内存交接（不经 epoll）。 |
62| **eventfd** | Linux 轻量事件通知原语。Go runtime 内部偶用于唤醒 netpoller 轮询线程，pairec 业务代码不直接接触。 |
63| **Grunnable / Gwaiting / Grunning** | goroutine 的三种状态：可运行（在 P 队列等跑）、等待（挂 netpoller/channel/wg，不占 M）、运行中（占 P-M-CPU）。 |
64| **fan-out / fan-in** | fan-out = 一个任务拆成多个子任务并发；fan-in = 多个子任务结果合并回一处。pairec 用"buffered channel + 固定计数循环"做 fan-in。 |
65| **fire-and-forget** | 派生 goroutine 后不等返回（用于日志/埋点等不阻塞响应的副作用）。 |
66| **singleflight** | Go 标准库 `golang.org/x/sync/singleflight`：并发同 key 请求合并成一次后端调用。**pairec 未用**，是高并发缓存击穿的根因（§3.4、§6.4）。 |
67| **RTT** | Round-Trip Time，一次网络往返时延（此处理论指到 Redis/Hologres/EAS 的往返）。 |
68| **STW** | Stop-The-World，Go GC 暂停所有 goroutine 的阶段，是 p99 尾部抖动来源。 |
69| **p99** | 延迟分布的 99 分位（还有 p999 等），衡量尾延迟。高 QPS 下 p99 抬升是本文关注核心。 |
70| **clone（AB clone）** | pairec 的 AB 实验机制：`CloneWithConfig(params)` 用每实验参数克隆一个实例副本，不污染共享基实例。 |
71| **AST** | Abstract Syntax Tree。精排的 `RankScore` 打分表达式以 AST 形式逐 item 求值（CPU）。 |
72| **admission filter** | TinyLFU 缓存的准入策略，过滤掉大概率不会被再次访问的 key，降低长期 miss 率。 |
73| **matmul** | 矩阵乘法。DPP 排序的 CPU 热点核心（gonum dense 实现）。 |

91### 1.1 逻辑视图
92
93pairec 进程内是"分层 + 注册抽象"结构。核心是**一个请求经编排层串起多个 stage service，stage 通过全局注册表查实例、通过 AB clone 注入实验参数**：
94
95```
96┌────────────────── HTTP 路由层 (web/ + controller.go) ──────────────────┐
97│ net/http ServeMux → ControllerRegister.ServeHTTP (controller.go:29)    │
98│   defer recover → 500                                                  │
99│ Route("/api/recommend") → RecommendController (reflect 建 instance)    │
100│   Process: 读 body → UUID requestId → CheckParameter → makeContext     │
101│            → doProcess → 序列化 ItemData[] 响应                        │
102├──────────────────── 编排层 (service/) ─────────────────────────────────┤
103│ UserRecommendService.Recommend (user_recommend.go:46)  ← 唯一编排心    │
104│   ├─ LoadUserFeatures          (user 特征预取)                          │
105│   ├─ go pipeline.Recommend     (第二路径, 并发)                         │
106│   ├─ RecallService.GetItems    (主路径召回, 并发扇出)                   │
107│   ├─ Filter                    (主路径过滤)                             │
108│   ├─ GeneralRankService.Rank    (粗排/冷启分流)                         │
109│   ├─ FeatureService.LoadFeatures (item 特征装配)                        │
110│   ├─ RankService.Rank           (批 EAS 精排)                           │
111│   ├─ wg.Wait + mergePipelineItems (双路合并)                           │
112│   ├─ Sort                       (多策略重排)                           │
113│   └─ 截断 size + fire-and-forget 日志/hook                             │
114├─────────────── 可插拔注册层 (register.go + 各 *.Load) ────────────────┤
115│ 全局 map[name]instance 工厂模式:                                       │
116│   recall.RegisterRecall / sort.RegisterSort / filter.RegisterFilter    │
117│   Load(config): 按 Type 大 if-else 分发 New<Type>(conf)                 │
118│   md5-sign 跳过: 配置未变则不重建 (recallSigns, sortSigns)              │
119│   ICloneRecall/ICloneSort: AB 参数 override 不污染基实例               │
120├──────── 数据访问层 (module/*_dao.go + persist/ + datasource/) ────────┤
121│ 一接口多后端: feature_dao → redis/hologres/mysql/clickhouse/hbase/...   │
122│ persist/cache: localCache(go-cache) / redis                             │
123│ module/feature_dao.go: in-proc TinyLFU(goburrow) + 100ms 超时           │
124│ algorithm/: eas/tfserving/milvus/faiss/seldon (外部模型服务 HTTP/gRPC) │
125└────────────────────────────────────────────────────────────────────────┘
126```
127
128关键抽象：**一个数据需求 = 一个接口 + N 个后端实现**。后端选择由配置驱动，换后端是改配置不是改代码。这决定了负载画像可由配置完全重塑——同一编排层，配 Redis 还是 Hologres，I/O 画像天差地别。

145**进程内无独立 worker pool**——所有并发都是"按请求即时派生 goroutine"模式,无全局长生命周期 worker 池。这是 pairec 并发模型的关键特征,决定了 §6 的并发负载形态。

147### 1.3 物理视图（节点级）
148
149单节点部署一个 pairec 进程,对外 HTTP(默认 8000,可配)。进程内依赖的外部后端(Redis/Hologres/MySQL/EAS/Milvus 等)通过配置注入,进程本身无状态——状态全在外部后端。进程内缓存(TinyLFU、go-cache)是 per-instance 的 in-process 缓存,进程重启即失。

181### 2.1 处理过程(编排层内部 stage 语义)
182
183```
184POST /api/recommend  {uid, size=10, scene_id, category}
185    │
186    ▼ [web/recommend_controller.go:Process]
187    生成 requestId(UUID) → CheckParameter(默认 size=10, scene=default_scene)
188    → makeRecommendContext(建 RecommendContext + AB MatchExperiment)
189    → NewUserRecommendService().Recommend(ctx)   ← 编排心入口
190    │
191    ▼ [user_recommend.go:46 Recommend]
192    LoadUserFeatures(user, ctx)                   user 特征预取
193    │
194    ├─(goroutine) pipeline.Recommend(user,ctx)   ← 第二路径 [pipeline.go:45]
195    │     scene → userRecommendSceneMap[scene] → N 个 pipeline.UserRecommendService
196    │     每个并发跑: Recall→Filter→GeneralRank→Feature→Rank→ColdStartRank→Sort
197    │
198    ├─(同步 主路径):
199    │   RecallService.GetItems(user,ctx)         [recall.go:54] 并发扇出
200    │     scene+category → recallNames → 每路一个 goroutine (defer recover)
201    │     → buffered chan 合并 → items[]
202    │   Filter(items)                            [recommend.go:33] 顺序过滤
203    │   GeneralRankService.Rank(items)            粗排/冷启分流
204    │   FeatureService.LoadFeatures(items)       item 特征装配 (隐藏 I/O 热点)
205    │   RankService.Rank(items)                   批 EAS 精排
206    │
207    ▼ wg.Wait() [user_recommend.go:143]
208    mergePipelineItems(items, pipelineItems)     [user_recommend.go:189]
209       (同 id 合并属性, pipeline-only 追加)
210    │
211    ▼ Sort(items) [recommend.go / sort.Sort]    多策略重排
212    截断 size → items[:size]
213    │
214    ▼ fire-and-forget: FeatureLog / LogSampleResult / CleanHooks (各起 goroutine)
215    │
216    ▼ [web/recommend_controller.go:doProcess]
217    序列化 ItemData[] → io.WriteString (注意: 响应体只含 item_id/item_type/retrieve_id, 不含 score)
218```
219
220**关键细节(源码确认)**:
221- 主路径与 pipeline 路径**并行**而非串行(`user_recommend.go:74-83` 的 `go func` + `wg.Wait`)。两路召回解耦:主路径用 `RecallService`(按 category 解析召回名),pipeline 路径按 scene 选 pipeline 配置。
222- merge 是 **属性合并**(同 id 的 item 合并 properties,pipeline-only 的追加),非简单拼接(`user_recommend.go:189-204`)。

443- **G0(主 goroutine)**:整条链反复在"网络 I/O 等待 / channel 等待 / CPU 计算"间切换,阻塞点在 t1/t3/t6/t7/t8。阻塞时 G0 解绑 M,挂到 netpoller 或 channel 等待队列——**不占线程、不占 CPU**。
444- **M(线程)数**:网络 I/O 不膨胀 M(netpoller 接管);仅尾部文件日志短暂绑 M。**进程内 M 数 ≈ GOMAXPROCS + 少量空闲复用,不会随 QPS 线性膨胀**——这是与"每连接一线程"模型的关键区别,也是 pairec 能扛高并发的根因。
445- **CPU 利用率**:由"可运行 G 数 vs GOMAXPROCS"决定。I/O 密集期可运行 G 少(都在 netpoller 挂着),CPU 可能**空闲**(请求被 I/O 卡);DPP/AST 期 G0 占 P 满载。
446- **唤醒与竞争**:G 的唤醒来自两条异步通道——① netpoller(后端响应到达,epoll 就绪);② channel/wg(其他 G 投数据或 wg 归零)。唤醒后的 G 进 P 运行队列,与所有其他可运行 G **争抢 P 槽**(数量=GOMAXPROCS)。竞争失败的 G 排队,等待时间累积成 p99。

448### 3.2 分:GMP 模型与三类阻塞/唤醒
449
450**goroutine 是 Go runtime 管理的用户态轻量执行单元**(栈初始 2KB、可增长,创建约几百纳秒),与 OS 线程、CPU 由 GMP 模型桥接:
451
452```
453  G (goroutine) ──┐                    ┌── CPU 物理核
454                  │ 被 P 调度           │ (执行指令的唯一实体)
455  G ──────────────┤                    │
456  G ... (无上限)  ├─ P (调度器) ───────┤── M (OS 线程) ─绑定─┘
457                  │  容量=GOMAXPROCS   │  (OS 调度的实体, 复用)
458  全局运行队列 ◄───┘                    │
459                  └── netpoller (epoll): 网络就绪的 G 在此等, 不占 M
460                     channel 等待队列: 等 <-ch / wg 的 G 在此, 不占 M
461```
462
463- **G : P : M : CPU核 = N : K : K : 核数**(K=GOMAXPROCS≤核数)。G 数无上限,M 数 ≈ K + 复用。
464- `GOMAXPROCS` 由 `automaxprocs`(`pairec.go:44`)按 cgroup 配额校准。假设容器 4 核 → P=4,**同时占 CPU 的 G 最多 4 个**。
465
466**三类阻塞及其唤醒/竞争(修正版)**:
467
468| 阻塞类型 | G 去哪 | M(线程) | P | CPU | 唤醒的底层机制 | 竞争逻辑 |
469|---|---|---|---|---|---|---|
470| **网络 I/O**(Redis/Hologres/EAS,热路径全部) | 解绑 M,挂 netpoller | **释放,不膨胀** | 让给别的 G | 跑别的 G 或空闲 | **epoll**:内核网卡收到包→硬中断→软中断→epoll_wait 就绪→netpoller 把 G 标 Grunnable | 醒后入 P 队列争 P 槽 |
471| **channel/wg 等待**(`<-ch`/`wg.Wait`) | 挂 channel 等待队列 | 不占 | 让给子 G | 跑子 G 或空闲 | **futex + atomic**:生产者原子改 channel 状态,若发现有人在等,通过 futex wake 唤醒;wg 是 atomic 计数,futex wake | 同上,与所有可运行 G 争 P |
472| **CPU 计算**(DPP/AST/Sort) | Grunning 占 P-M | 占住跑 | **被占** | 满载 | **无需唤醒**:G 主动在 CPU 上跑,时间片到被 runtime 抢占(preemption)回 Grunnable | G0 独占 P,其余 G 排队(长杆阻塞他人) |
473| 文件 I/O(尾部日志,非热路径) | 绑 M 阻塞 | 占住陷内核 | 让出 | 跑别的 | 阻塞 read/write,内核 I/O 完成后唤醒 | 仅尾部,影响小 |

475**唤醒/等待的底层机制详解(结合 pairec 实际使用)**:
476
477Go runtime 把"等待/唤醒"分成两条完全不同的路径,pairec 都用到了。理解这两条路径是理解 pairec 并发模型的关键:
478
479**(1) 网络等待 → netpoller(epoll + 硬中断)**
480
481pairec 热路径的召回(`recall.go:156` GetCandidateItems 调 Redis/Hologres)、精排(`rank_service.go:273` algorithm.Run 调 EAS)、特征(`feature_hologres_dao.go` 调 Hologres)全是网络 I/O。Go 把它们统一交给 **netpoller**,底层是 Linux `epoll`:
482
483```
484goroutine 调 redisConn.Get(key)           // redigo 内部最终调 net.Conn.Read
485  → Go runtime 把 fd 注册到 epoll (epoll_ctl ADD)
486  → goroutine 解绑 M,状态变 Gwaiting,挂到 netpoller 的等待结构
487  → M 释放回线程池(P 也释放给别的 G)         ← 不占线程,这是关键
488
489  ...后端处理...
490
491  → 网卡收到响应包 → 触发硬中断(IRQ)
492  → 内核软中断(softirq)处理协议栈 → 把数据放进 fd 的 socket buffer
493  → epoll_wait 返回该 fd 就绪
494  → Go runtime 的 netpoller 轮询(或被 sysmon 唤醒)发现就绪 fd
495  → 把对应的 G 标记 Grunnable,放进 P 的运行队列
496  → 该 G 重新争 P-M-CPU 执行,拿到数据继续跑
497```
498
499关键点:**这条路径的"等待方"完全不占 M**。epoll 一个线程管所有 fd(Go runtime 内部只用少量 M 轮询 epoll),所以 pairec 即使有 4 万个 G 同时在等网络响应,M 数也不会涨——这是与"每连接一个阻塞线程"模型的本质区别。**唤醒的成本**:一次硬中断 + 软中断 + epoll_wait 返回 + runtime 调度,是异步的、批量的(epoll 一次可返回多个就绪 fd,所以"一波响应同时到"只触发一次 epoll_wait)。
500
501**(2) channel/wg 等待 → futex + atomic(纯用户态,不走 epoll)**
502
503pairec 的 fan-in 合并(召回 `recall.go:169` `<-ch`、pipeline `pipeline.go:62` `<-ch`、精排 `rank_service.go:309` `<-responseCh`、`wg.Wait()` 多处)都是 channel/sync.WaitGroup 等待。它们的底层是 **futex**(Linux fast user-space mutex)+ atomic,与网络 I/O 的 epoll 路径完全不同:
504
505```
506// channel 等待(recall.go:169 G0 在 <-ch 等)
507G0 调 <-ch:
508  → Go runtime 检查 channel 的环形缓冲,空 → 无数据可拿
509  → 把 G0 挂到 channel 的等待队列(一个 sudog 结构),状态 Gwaiting
510  → G0 解绑 M,P 让给别人                ← 同样不占 M
511  → runtime 调度别的 G 跑
512
513// channel 唤醒(recall.go:165 G-recall 投 ch <- items)
514G-recall 调 ch <- items:
515  → 把数据放进 channel 环形缓冲
516  → 原子操作发现有人在等(等待队列非空)
517  → runtime 把等待的 G0 弹出队列,标记 Grunnable,放进 P 运行队列
518  → 若目标 G 在别的 M/P 上,可能触发 futex wake 或向那个 P 发检查信号
519     (runtime 用 IPI/信号让别的 P 尽快调度它,但这不是每用户调用必发)
520  → G0 醒后从 <-ch 返回,拿到 items 继续
521```
522
523关键点:channel 等待**也不占 M**(G 挂起解绑 M)。唤醒靠 runtime 内部的等待队列 + atomic + 必要时 futex,不走 epoll(因为这不是网络事件,是内存中的数据交接)。`sync.WaitGroup` 同理:wg.Wait 检查 atomic 计数,非零则挂起;wg.Done 原子减一,减到零时 runtime 唤醒所有 Wait 的 G。
524
525> **为什么不提 eventfd**:Go runtime 在 Linux 上**用 epoll 监听网络 fd**,但 channel/wg 的等待**不通过 eventfd**,而是 runtime 自己管理的用户态等待队列 + futex。eventfd 主要用于"唤醒 runtime 的 netpoll 轮询线程"这类场景(pairec 不直接接触)。所以 pairec 的等待唤醒实际是:**网络等 epoll+中断、内存交接等 futex+atomic、CPU 计算无需唤醒**——没有第三种。
526
527**(3) CPU 计算 → 无等待,靠抢占(preemption)**
528
529DPP/AST/Sort 这种纯 CPU 段,G 一直在 Grunning 跑,没有"等待"也没有"唤醒"。Go 1.14+ 的**异步抢占**保证:即使 G0 在跑长 CPU 循环(如 DPP 的 O(n³) matmul),runtime 的 sysmon 线程会发现它跑太久,通过发信号(基于信号的抢占)把它打断回 Grunnable,避免独占 P。所以 pairec 的 DPP 长杆**不会饿死整个 P**,但会让其他 G 等一个抢占周期。
530
531> **核心修正**:网络 I/O 经 netpoller,G 阻塞时解绑 M,不占线程。**pairec 的 M 数稳定在 GOMAXPROCS 量级**,高并发真正的代价是"可运行 G 堆积→争 P→调度延迟",而非线程爆炸。这对 OS 研究很重要:不能把 pairec 当成"每连接一线程"模型来测线程开销。
532
533**对 OS 研究的承重启示**(把上面三类映射到 OS 观测点):
534
535| pairec 现象 | OS 层实际在发生什么 | OS 该观测什么 |
536|---|---|---|
537| 4 万 G 等 I/O | 4 万 fd 在 epoll 树上,M 不涨 | epoll fd 数、`/proc/<pid>/netstat` 软中断计数,**不是**线程数 |
538| 一波响应到 → p99 抖 | 批量 epoll_wait 返回 → 大量 G 同时 Grunnable → 争 P | P 运行队列长度、调度延迟(`/proc/schedstat`、`runtime/trace`) |
539| DPP 长杆 | 1 个 G 跑 O(n³),被 sysmon 异步抢占 | CPU 核占用、抢占信号数(`signal 信号`) |

574### 3.5 实战:高并发(QPS=1000)下一请求的端到端处理流程
575
576把 §3.1-§3.4 的概念放进一个具体场景:容器 4 核(P=4),1000 QPS 持续注入,每请求 §3.3 的 40~50 个 G。跟踪**其中一个请求 G0**从到达到响应,看分发/并发/阻塞/唤醒/竞争:
577
578```
579[t0 到达] 1000 个 G0/秒涌入 net/http accept。每个 G0 进入 Process。
580           进程内已有 ~4万 G:其中绝大多数挂在 netpoller 等 I/O,
581           可运行(争 P)的瞬时可能只有几十~几百个。
582           → G0a(我们跟踪的这个)进 P 运行队列,与其他可运行 G 争 4 个 P 槽。
583
584[t1 用户特征] G0a → LoadUserFeatures → DAO Redis 读。
585           G0a 解绑 M 挂 netpoller (Gwaiting)。M 释放给别的 G。
586           → 此时 G0a 不占 CPU。若 P 队列前有别人的 CPU 任务,别的 G 在 CPU 上跑;
587           若都在 I/O,4 个 P 可能部分空闲 (CPU 利用率下降 — I/O bound 期)。
588           唤醒: Redis 响应到 → netpoller 标 G0a runnable → 入队争 P。
589
590[t3 召回]   G0a 派生 5 个 G-recall (R=5),各自挂 netpoller 等 5 路后端。
591           G0a 在 <-ch 等 (Gwaiting)。
592           → 此刻这 6 个 G 都不占 CPU。进程内同时有 ~1000 个 G0 × 类似状态。
593           唤醒竞争: 5 路 Redis/Hologres 响应陆续到, 每到一个醒一个 G-recall,
594           ch<-items 后结束。G0a 被 channel 唤醒, 重新争 P。
595           关键: 若 5 路后端都慢, G0a 长挂; 若某路 panic→recover→空切片, 不报错, 不影响其他。
596
597[t6 特征]  G0a 派生 4 个 G-feat, 每个 G-feat 再 fan-out 4 个 DAO worker (cpuCount=4),
598           共 16 个 G 挂 netpoller 等 Hologres。G0a 在 wg.Wait 等。
599           → 这是单请求内"并发后端调用密度"高峰: 16 个并发 SQL。
600           进程级: 1000 请求 × 16 = 1.6万 并发 SQL 在途 → Hologres 连接池(maxOpen=100)
601           成天花板, 后到的 SQL 在池里排队 (不在 netpoller, 在 db.Wait 排队) → 链式延迟。
602           唤醒: SQL 返回 → DAO worker 醒 → 写结果 → G-feat wg-- → G0a 醒。
603
604[t7 精排]  G0a 派生 外层2×内层3=6 个 rank G + customRanks, 各挂 netpoller 等 EAS。
605           → EAS MaxIdleConnsPerHost=2000, 1000 请求 × 6 = 6000 并发 EAS 在途,
606           超 2000 的部分排队。AlgorithmFactory.mutex RLock 每次 algo 调用抢一次
607           (进程级唯一热锁, 6000 并发轮流 RLock, 稳态争用低但热加载写锁时全堵)。
608           唤醒: EAS 响应到 → 内层 G 醒 → wg-- → 外层 G 投 responseCh → G0a 醒。
609           CPU 段: 全部回来后 AST 求值逐 item 算分 (CPU, G0a 占 P)。
610
611[t8 汇合]  G0a wg.Wait 等 G-pipe。若 G-pipe 跑得慢 (它也要走召回→…→精排),
612           G0a 在此长挂 — 无超时, 长尾放大点 (§3.6.5)。
613
614[t9 重排]  G0a 跑 Sort (DPP)。纯 CPU, G0a 独占一个 P。
615           → 若 DPP n>200, 此段 CPU 长杆: G0a 占 P 跑几十 ms,
616           期间其他 3 个 P 服务别的请求, 但第 4 个 P 槽被 G0a 长占,
617           排队的可运行 G 多等一个 P 槽 → 调度延迟累积。
618           (注: DPP 用 gonum dense, 无 LockOSThread 绑核, 无 cache 局部性)
619
620[t10 响应] G0a 截断 + 派生 fire-and-forget(FeatureLog 等写文件, 绑 M 但响应已发)
621           + return。net/http 回写响应, G0a 结束。
622```
623
624**实战结论(端到端看到的进程内图景)**:
625- **G 总数 4~5 万,M(线程)数稳定 ~4**:不会线程爆炸,因为网络 I/O 全走 netpoller。OS 若按"线程数"观测 pairec 会得出"压力不大"的错误结论——真实压力在 **P 调度队列长度**和 **netpoller 待唤醒 G 数**。
626- **三处 P 竞争爆发点**:① 一波 EAS/Redis 响应同时到,瞬间大量 G 转 runnable;② 特征 DAO 16 路并发同时 SQL 返回;③ DPP 长杆独占 P。这三点决定 p99。
627- **两处连接池天花板链式延迟**:Hologres maxOpen=100、EAS MaxIdleConnsPerHost=2000——超限的在 db/EAS 客户端内部排队(非 netpoller,非 P 队列),是另一种阻塞,DAO 100ms 硬超时兜底→部分结果。
628- **无取消传播的代价**:1000 请求里若客户端断连,G0a 在途的召回/SQL/EAS **不取消**,白跑完才丢弃——QPS 高时这是可观无效负载,是 OS 层"取消传播"优化的输入(§7.2)。

632## 3.6 主路径 vs pipeline 路径:配置维度、编码差异与协作关系
633
634编排心 `UserRecommendService.Recommend`(`service/user_recommend.go:46`)在 `:75` 派生一个 goroutine 跑 pipeline 路径,自身继续跑主路径,`:143` `wg.Wait` 汇合后 `:144` 合并。这一节把两条路径**到底差在哪、为什么需要 pipeline**讲透——这是后续做扩展层(生成式召回/精排)时的架构判断基座。
635### 3.6.1 框定修正:不是"保底 vs 可配置",而是"并列完整管线"
636
637> **承重更正**:不要用"保底召回 vs 可配置多策略召回"框定两条路径。这个说法自相矛盾(既说两者都是完整管线,又说一个是另一个的 fallback),且与源码不符。正确框定见下。
638
639两条路径都是完整的推荐管线(召回→过滤→粗排→特征→精排→重排),**主路径必跑、pipeline 路径可选**(scene 在 `PipelineConfs` 未配时 `pipeline.Recommend` 直接返回 nil,整条路径不存在,`pipeline.go:48`)。配了的话两者**并列并行**,不是保底关系——主路径召回空了不会自动切到 pipeline 顶上,主路径空列表照样走完后续 stage。注册层(全局工厂 `map[string]Recall` / `map[string]ISort` / filter)是两者的**共同底座**,不存在"主路径一套注册、pipeline 另一套"。
640
641真正的 fallback 语义在另一个函数 `TryRecommendWithFallback`(`user_recommend.go:206`,基于 `fallback.DefaultFallbackService`),**`/api/recommend` 不走它**——两条路径的并行合并与 fallback 是两套独立机制,不要混为一谈。

643### 3.6.2 决定性差异:配置维度(主路径 scene 单槽 vs pipeline 多编排链)
644
645这是两条路径存在的**真正理由**,也是"为何需要 pipeline"的答案所在。差异不在编码,在**配置绑定维度**:

647```
648主路径:所有 stage 配置按 scene 一个维度解析(运行时动态取)

695这两个是**不同维度**的问题,混淆它们就会得出"pipeline 没用"的错误结论:
696
697- **多路召回** = 一套编排内,召回阶段并行多路。**主路径原生支持**:`RecallNames` 是 `[]string`,挂几路召回就配几个名字,`recall.go:132` `make(chan, len(recalls))` 每路一个 goroutine 并发。生成式召回只要 `RegisterRecallWithConfig` 注册成某个名字塞进 `RecallNames` 即可,**不需要 pipeline**。pairec4tigerllm 的 `GenerativeRecall`/`MilvusRecall`/`QuotaMultiRecall` 就是这么挂进主路径的。
698- **多套编排** = 一次请求里**并行跑多条完整推荐链**,各自有独立召回名单/独立精排/独立重排,最后合并。**主路径做不了**:一个 scene 只有一个 `RankConf` 槽、一个 `SortStrategies` 槽。要在同一次请求并行跑两套不同精排模型,必须靠 `PipelineConfs[scene]` 挂多个 pipeline。
699
700**一句话**:多路召回是"召回阶段内并行多路",pipeline 是"编排级别并行多链"。前者主路径够,后者必须 pipeline。
701
702### 3.6.5 执行流与唯一合并点
703
704**并行执行**,唯一合并点在**精排之后、重排之前**:
705
706```
707G0 (主请求 goroutine)
708├── :64  LoadUserFeatures (阻塞 G0,用户特征加载)
709├── :75  go func() { pipelineItems = pipeline.Recommend(...) }  ← 派生 G-pipe
710├── :83  recallService.GetItems   (主路径召回, G0 同步, 内部 M goroutine 扇出)
711├── :105 Filter                    (G0)
712├── :116 generalRankService.Rank   (G0)
713├── :129 featureService.LoadFeatures(G0, 内部可能 async 扇出)
714├── :137 rankService.Rank          (G0, 内部两级 goroutine 嵌套)
715├── :143 wg.Wait()                 ← 唯一 join 点:等 G-pipe 完成
716├── :144 mergePipelineItems(items, pipelineItems)  ← 唯一合并点
717├── :151 Sort                      (G0, 合并后统一重排)
718└── :168 items[:size] 截断 → 响应
719
720  G-pipe 内部(pipeline.Recommend, pipeline.go:45):
721  ├── scene → userRecommendSceneMap[scene] → N 个 pipeline service
722  ├── N 个 goroutine 各跑完整 stage 链(含 ColdStartRank)
723  └── 固定计数循环合并 N 路结果 → pipelineItems
724```
725
726**关键时序事实**:
727- 主路径 5 个 stage(召回→过滤→粗排→特征→精排)与 pipeline 路径**物理时间重叠**——主路径跑召回的同一时刻,pipeline 路径也在跑自己的召回→…→精排。
728- 合并语义(`mergePipelineItems`, `:189-204`):**按 item id 的并集 + 属性叠加**。同 id item 把 pipeline 路径算出的 properties 叠加到主路径 item;不同 id item 直接追加。**不是择优、不是去重**,所以两条路径 score 不需要可比——最终顺序由合并后唯一的 Sort 决定。
729- **无超时 join**:主路径精排早跑完,只要 pipeline 路径没回来,`wg.Wait()` 阻塞 G0,Sort 推迟。**慢路径决定请求延迟**,长尾在此放大——这是双路径架构的固有代价。
730
731### 3.6.6 决策表:做生成式召回 + 生成式精排,要不要用 pipeline
732
733| 诉求 | 仅主路径 | 用 pipeline |
734|---|---|---|
735| 多路召回(含生成式召回) | ✅ `RecallNames` 列表 + `RegisterRecallWithConfig` | 杀鸡用牛刀 |
736| 生成式精排 | ✅ 注册成 rank,配进 `RankConf[scene]` | 同上,不划算 |
737| 同一 scene 同一次请求并行跑**多套不同精排模型** | ❌ 一个 scene 一个 RankConf 槽 | ✅ 每个 pipeline 独立 RankConf |
738| 召回结果与主路径**并行叠加**(不替换上线) | ❌ 主路径单链 | ✅ `wg.Wait`+`mergePipelineItems` 并集合并 |
739| 实验性召回链补冷启动 | ❌ 主路径无 ColdStartRank | ✅ pipeline 自带 `coldStartRankService` |
740
741**对扩展层(生成式召回/精排)的架构判断**:如果"生成式召回"只是多一路召回源、"生成式精排"只是换/加一个精排模型,**主路径一条链足够,不要引 pipeline**——pipeline 的双路径、`wg.Wait` 长尾放大、合并语义、ColdStartRank 分支是不划算的复杂度。**只有当需要在同一次请求并行跑多套编排不同(召回名单不同、精排模型不同)的推荐链且要并集合并时**,才动用 pipeline。这是 pairec 上游设计 pipeline 的本意。

793### 4.2 三个真正的瓶颈(进程内)
794
7951. **特征装配是隐藏的 I/O 长杆**。在 rank 前运行,多个 Feature config 时总 RTT = Σ chunk,每个 100ms 超时兜底。冷缓存下可吃满多个并发 SQL 连接(Hologres maxOpen=100)。`async=true` 时全并发,瞬时连接飙升。
7962. **DPP/SSD 重排是 CPU 长杆**(O(n²)~O(n³), `dpp_sort.go:464-473`)。靠 `candidateCnt`/`minScorePercent` 预截断 + `abortRunCnt` 短路缓解;配置不当让 n>200 时 CPU 飙升。gonum dense matmul 在主 goroutine 跑,阻塞该 pipeline goroutine 对应的 P。
7973. **`AlgorithmFactory.mutex` 是热路径唯一进程级锁**。每次 EAS 调用 RLock,QPS 高时累积争用可见。虽是 RLock(读共享),但热加载时的写锁会阻塞所有读。
798
799### 4.3 每环节"打"在什么系统资源上
800
801- **召回/特征/精排的 I/O 路径**:打在 TCP 栈、连接池、后端网络 RTT。Go 侧网络 I/O 走 netpoller,不膨胀 M(线程);GOMAXPROCS 钳住 P,瓶颈转化为"可运行 G 争 P 的调度延迟"。
802- **DPP/AST sort 的 CPU 路径**:打在 CPU 核 + 内存带宽(n² 矩阵)。无亲和性绑定。
803- **in-proc 缓存(TinyLFU/go-cache)**:打在进程堆内存 + GC。Go GC STW 与缓存容量权衡。

807## 5. 节点规模放大分析(单系统内)
808
809"规模变大"在编排层有三处含义:候选集 S 变大、特征数 F 变大、召回路数 N 变大。逐一分析对**单节点资源**的影响:
810
811| 规模维度 | 影响环节 | 资源影响(单节点内) |
812|---|---|---|
813| **S↑(候选数)** | DPP/SSD | CPU **二次~三次方**膨胀, `dpp_sort.go:464` matmul 是热点; n>200 后 CPU 长杆可能反超 I/O 长杆 |
814| S↑ | Rank EAS | batch 数 `ceil(S/100)` 线性增, EAS 调用数线性增; 网络连接/RTT 线性 |
815| S↑ | 特征 DAO | Hologres chunk=600, `cpuCount=ceil(S/600)` goroutine 线性增; 连接池 maxOpen=100 是天花板, 超了排队 |
816| S↑ | Bloom/state filter | batch=500 固定, RTT 数 `ceil(S/500)` 线性增 |
817| **F↑(特征数)** | FeatureService | Feature config 数线性增, 总 RTT=Σ chunk; `async=true` 时全并发→瞬时连接飙升 |
818| F↑ | in-proc TinyLFU | `CacheSize` 决定内存占用; F 大且 `CacheSize` 未调→命中率降→后端压力升 |
819| **N↑(召回路数)** | RecallService | 召回 goroutine 线性增, 并发后端连接线性增 |
820| N↑ | merge | merge 是 sub-ms CPU, 不构成瓶颈 |
821
822**单节点内的拐点**:
823
824- **CPU 拐点**:DPP 让 n 越过 ~200 时, CPU 长杆超过 I/O 长杆。这是 OS 研究里"CPU 调度 vs I/O 调度"的切换点。
825- **连接池拐点**:Hologres maxOpen=100、EAS MaxIdleConnsPerHost=2000、Redis MaxIdle(配置驱动,**无代码默认→0 是隐患**)。规模大到并发 DAO 批次超过池上限时, I/O 排队, p99 抬升。
826- **内存拐点**:TinyLFU `WithMaximumSize` + DPP 500k embedding LRU(`dpp_sort.go:77`)+ Redis pool。规模↑ + 命中率↓ → 内存占用涨、GC 压力涨(Go GC STW)。`itemStmtMap` 按 IN-list 长度 key 的预编译缓存**无 eviction**(`feature_hologres_dao.go:581`), 规模下 batch size 抖动会让该 map 无界增长——这是已确认的 gap。

830## 6. 多请求并发分析(QPS↑)
831
832并发上升时,资源争用画像(基于 §3 的扇出结构 + §4 的池上限):
833
834### 6.1 goroutine 数与调度延迟
835
836```
837QPS↑ → 并发 HTTP goroutine↑ (1 conn = 1 goroutine)
838     → 每请求再扇出: 召回 N + DAO cpuCount + rank batch×algo
839     → 瞬时 goroutine 数 ≈ QPS × (N + cpuCount + batch×algo)
840     → GOMAXPROCS (automaxprocs 按 cgroup) 钳住 P → 可运行 goroutine 排队 → 调度延迟↑
841     → 网络 I/O (N×M 个并发后端调用) 走 netpoller 不膨胀 M, 但可运行 G 堆积 → 争 P → 调度延迟↑
842```
843
844**关键量化**:单请求派生数十 goroutine(§3.1),QPS=1000 时进程内 goroutine 数可达数万。GOMAXPROCS(如 cgroup 限 8 核)钳住 P=8,可运行 goroutine 排队,调度延迟成为 p99 抬升源。
845
846### 6.2 连接池天花板
847
848| 后端 | 池上限 | 并发超限后果 |
849|---|---|---|
850| Redis | `MaxIdle`(配置驱动,无默认→0 隐患) | 连接耗尽→排队 |
851| Hologres | maxOpen=100(env 可调) | 并发 SQL 批次>100→排队 |
852| EAS | MaxIdleConnsPerHost=2000(EasyRec SDK 路径 2000) | 高 QPS+多 algo 下可能触顶 |
853
854### 6.3 锁争用累积
855
856- `AlgorithmFactory.mutex` RLock:QPS 高时累积,热加载写锁时短暂阻塞所有读。
857- 其余锁 per-instance,争用不随 QPS 显式恶化。
858
859### 6.4 无 singleflight 的击穿
860
861热点用户/物品的 cache miss 在并发下直打后端:多个请求同一 key 同时 miss→同时打后端→后端 QPS 雪崩。这是 OS 层"请求合并/dedup"的典型优化点。in-proc TinyLFU 的 TinyLFU admission filter 降低长期 miss 率,但**不合并并发 miss**。
862
863### 6.5 失败模式与"部分结果"语义
864
865无请求级 context、无 errgroup,超时=部分结果(`feature_hologres_dao.go:627` 的 `select ctx.Done() return`)。高并发下后端变慢→更多请求走到 100ms 超时→返回更少候选→上游 `code:299 items size not enough`。这是"超时传播但取消不传播"的典型系统行为——OS 研究可关注"部分降级下的资源回收"。
866
867### 6.6 内存与 GC
868
869QPS↑ → in-proc 缓存填充↑ → 堆涨 → GC 频率↑ → STW 抖动。无 GC 调优配置暴露,默认 GOGC=100。高 QPS 下 GC STW 是 p99 尾部的重要贡献。

873## 7. 面向 OS 下一代研究的输入与优化点(编排层内部)
874
875按"缺位即机会"组织,全部锚定在 pairec 编排层:
876
877### 7.1 请求合并 / dedup(singleflight 缺位)
878热点 key 的并发 cache miss 直打后端(`recall.go` 召回缓存、`feature_*_dao.go` 特征缓存均无 singleflight)。**OS 机会**:内核或运行时层的"并发相同请求合并"原语,对 KV/SQL 后端 RTT 去重。推荐场景的热点用户/物品使该优化收益高。
879
880### 7.2 取消传播与请求级生命周期
881`RecommendContext` 不接 HTTP `r.Context()`,客户端断连/超时不取消在途工作,DAO 超时硬编码在 `context.Background()`(`feature_hologres_dao.go:157,601` 等)。**OS 机会**:进程内的请求级取消传播(structured cancellation),让在途召回/DAO/EAS 能随客户端断连即时释放,砍掉高并发下的"幽灵计算"。
882
883### 7.3 CPU 二次方热点与亲和性
884DPP 的 O(n³) matmul(`dpp_sort.go:464-473`)在主 goroutine 跑、无核绑定。**OS 机会**:自动识别二次方 CPU 热点并卸载到 SIMD/加速器,或调度到隔离核组避免拖累 I/O 路径的 goroutine(P 抢占)。
885
886### 7.4 缓存层级与内存层级
887in-proc TinyLFU + go-cache + Redis + Hologres 是多层缓存,但层级间无统一淘汰策略,`itemStmtMap` 无界增长(`feature_hologres_dao.go:581`)。**OS 机会**:跨层缓存统一淘汰/预取策略、内存占用可观测与 GC 协同(Go GC STW 与 LRU 容量的权衡)。
888
889### 7.5 连接池自适应弹性
890Redis `MaxIdle` 无默认、Hologres maxOpen=100、EAS 2000,高并发下静默排队。**OS 机会**:连接池自适应弹性、网络栈层的跨请求批量合并(Redis pipelining 已用,但 SQL/EAS 的跨请求 batching 缺位)。
891
892### 7.6 goroutine 池化与公平调度
893所有并发按请求即时派生,无池化复用,高 QPS 下 goroutine 创建/回收开销累积,可运行 goroutine 排队。**OS 机会**:goroutine 池化复用、跨请求的公平调度(避免大请求饿小请求)。

928pairec 编排层是一个"深层 goroutine 扇出 + 注册抽象 + 多层缓存"的成熟 Go 推荐服务。单请求内并发遍布每个 stage(召回扇出、rank 两级嵌套、DAO 工作队列),但缺 singleflight、缺请求级取消传播、无全局长生命周期 worker pool。**双路径方面**:主路径与 pipeline 路径是"并列完整管线"而非"保底 vs 可配置",决定性差异在配置维度——主路径按 scene 单槽解析所有 stage,pipeline 按 PipelineConfig 绑定且 `PipelineConfs[scene]` 可挂多链;多路召回主路径一条链即可(无需 pipeline),多套编排并行才需 pipeline;pipeline 的 `PipelineName` 仅日志标签,过滤/排序退回 scene 级。进程内三个真瓶颈是:特征装配 I/O 长杆、DPP/SSD CPU 二次方长杆、`AlgorithmFactory` 进程级热锁。规模放大时 CPU 拐点(DPP n>200)与连接池拐点(Hologres maxOpen=100)是主要切换点;多请求并发下 goroutine 数与 GC 压力是 p99 尾部主因。**线程模型承重结论**:pairec 热路径全网络 I/O 走 netpoller,M(线程)数稳定在 GOMAXPROCS 量级不随 QPS 膨胀,真实并发代价在"可运行 G 争 P 的调度延迟"而非线程开销——OS 观测若只盯线程数会误判。OS 介入的最大机会在请求合并、取消传播、CPU 热点调度三处。
929
930报告全部结论锚定 pairec 上游源码,无臆测。

1158### B.4 三视角融合要点
1159
1160| 融合点 | 线程模型视角 | 数据流视角 | 高并发视角 |
1161|---|---|---|---|
1162| **召回扇出** | M goroutine + buffered chan + recover | 每路 1 RTT, channel 固定计数合并 | N 请求 × M 召回 → 连接池压力 + 击穿 |
1163| **rank 两级嵌套** | 外层 B + 内层 A goroutine + 双 channel | batch × algo EAS 调用, AST 求值回填 score | N × B × A → `AlgorithmFactory` 锁争用 + EAS 池天花板 |
1164| **特征 DAO fan-out** | cpuCount goroutine + 工作队列 chan | chunk 化批量取, 100ms ctx | N × cpuCount → SQL 连接池(100)天花板, 隐藏 I/O 长杆 |
1165| **pipeline 并行** | N goroutine + chan, 无超时/recover | 第二路径与主路径 `wg.Wait` join 后 merge | 慢 pipeline 拖整个请求, 无超时放大长尾 |
1166| **DPP sort** | 主 goroutine CPU, 无绑核 | O(n²~n³) matmul | n>200 时 CPU 长杆反超 I/O, 阻塞 P |
1167| **fire-and-forget** | 尾部短暂 goroutine | 日志/特征落盘 | off-path, 不阻塞响应 |

1169### B.5 关键的"并发交汇点"(最值得 OS 研究盯住)
1170
11711. **`wg.Wait()` join 点**(`user_recommend.go:143`):主路径与 pipeline 路径在此汇合。这是"长短杆"交汇——慢的路径决定请求延迟,且无超时,长尾在此放大。
11722. **rank 双 channel**(`rank_service.go:254,255`):工作队列 + 结果队列的 fan-out/fan-in,是 rank 阶段并发的核心结构。内层 `wg.Wait()` 是 algo 粒度合并,外层固定计数循环是 batch 粒度合并。
11733. **特征 async 分叉点**(`feature_service.go:88-106`):`FeatureSceneAsyncMap[scene]` 一个 bool 决定特征装配是并发还是顺序。隐藏的 I/O 长杆在此分叉/合并。
11744. **连接池 × goroutine 数交汇**:并发 DAO goroutine 数(N × cpuCount)× 池上限(Hologres 100)——超了就排队,是高并发 p99 抬升的物理根因。
